# Engineering Work Order — WO-2026-07-26-001

## Problem Statement
The `telemetry fleet` report (`tools/telemetry`) has not been updated for
`schemaVersion 2` device-status payloads, despite WO-2026-07-25-001 already
exposing the relevant fields in CurrentState. Confirmed by direct
investigation (Claude Code, grep-verified, no inference):

- `extractDeviceOsVersion()` (tools/telemetry:1124-1133) only reads the
  legacy nested `deviceOS.version` shape — it does not fall back to v2's
  flat `startup.deviceOS` string, so v2-only devices can show an
  unresolved Device OS. This is the exact gap Codex flagged as a side note
  in the original resetCount investigation.
- No code path reads `firmware.resetCount`, `startup.resetCount`,
  `startup.reason`, or `startup.deviceOS` anywhere in this tool.
- `deviceStatusLedgerData` technically carries `schemaVersion` on the wire,
  but nothing in the report reads or surfaces it — there is currently no
  way, in text or `--json` output, to tell which schemaVersion any device
  last reported on.
- "Schema: fleet-summary.v1" (tools/telemetry:912, printed at line 1232)
  is confirmed to be the report's own JSON output-contract version — a
  hardcoded literal, unrelated to device schemaVersion. No conflation
  exists in the code; any conflation was in how the output reads to an
  operator.

## Operational Impact
Operators cannot currently see, from the fleet's primary status report,
whether the schemaVersion 2 cutover (tied to the v21 firmware rollout) has
actually completed across the fleet, or trust Device OS values for any
device that has moved to v2. This blocks confident tracking of the soak
expansion and the PMIC-issue resolution question, which depend on knowing
the fleet is reporting on consistent, well-understood data.

## Repository, Branch, Build, and Device Scope
- Repo: `particle-fleet-operations`
- File: `tools/telemetry` only
- Applies fleet-wide; most immediately relevant to the six v21 soak devices

## Evidence
Claude Code investigation (research only, no changes made), citing:
tools/telemetry:912, :1232, :1124-1133, :834, :1119-1174. Grepped for
`resetCount`, `startup.*`, `firmware.*`, `deviceOS`, `schemaVersion` across
the full file — confirmed no existing read path for any v2 field.

## Approved Architecture / Fix
1. Add schemaVersion visibility: a per-device field/column showing last
   reported schemaVersion, plus a fleet-wide summary line (e.g. "Schema
   versions observed: v2 (6/6)").
2. Fix `extractDeviceOsVersion()` to fall back to the flat
   `startup.deviceOS` string when the legacy nested `deviceOS.version` is
   absent.
3. Surface `startup.reason` and `startup.epoch` as factual, display-only
   lifecycle information — consistent with the handover doc's "proceed
   with display-only support" guidance. Do not derive any health or
   anomaly signal from them.
4. Display `firmware.resetCount` and `startup.resetCount` under clearly
   distinct, labeled fields if shown at all — never merged, never
   interpreted as a single "reset count." Display-only; no health logic.
5. Since the JSON output shape is changing, evaluate whether the report's
   own contract version should move to `fleet-summary.v2` (its own
   versioning scheme — coincidentally the same number as the device
   schema, but a separate decision).

## Acceptance Criteria
- Report shows each device's schemaVersion (or an accurate fleet-wide
  summary) without requiring a raw data dump.
- A v2-only device with no legacy `deviceOS.version` field resolves its
  Device OS correctly via `startup.deviceOS`.
- `firmware.resetCount` and `startup.resetCount`, if displayed, appear
  under distinct, clearly labeled fields — never merged.
- No change in behavior for schemaVersion 1 devices.
- Missing Device OS (neither `deviceOS.version` nor `startup.deviceOS`,
  including empty/whitespace-only values) displays as "unknown"
  (`null` in JSON) — never inferred from `schemaVersion`.
- An unrecognized `schemaVersion` (not 1 or 2) is surfaced as its raw
  value, not coerced to a known version or treated as unhealthy.
- A malformed `schemaVersion` (non-scalar — object/array) displays as
  "unknown" rather than being stringified into output.
- Devices with no `deviceStatusLedgerData` at all still appear in the
  fleet summary/verbose table — new fields must not cause filtering,
  exceptions, or any health/anomaly classification change.
- Device OS resolution precedence (legacy `deviceOS.version` checked
  before `startup.deviceOS` fallback) is documented in code comments.

## Required Tests
- Unit test: device with only legacy `deviceOS.version` → resolves as before.
- Unit test: device with only `startup.deviceOS` (v2, no legacy field) →
  resolves correctly (this is the currently-broken case).
- Unit test: schemaVersion surfaced correctly for both v1 and v2 sample
  payloads.
- Regression test: v1-only fleet output unchanged from current behavior.
- Unit test: `startup.deviceOS` as empty string/whitespace → treated as
  missing, falls through to "unknown" (not treated as a valid value).
- Unit test: malformed/non-scalar `schemaVersion` → displays "unknown",
  no exception thrown.
- Unit test: device with no `deviceStatusLedgerData` at all → still
  appears in output, schemaVersion/deviceOS show as "unknown", no
  filtering or exception.

## Deferred (explicitly out of scope for this Work Order)
- Distinguishing "device never reported" from "device reported without a
  schemaVersion field" — if this distinction is ever needed, it should
  ride on an existing last-report/presence field rather than new logic
  invented here.
- Diagnostics for when `deviceOS.version` and `startup.deviceOS` are both
  present but disagree — legacy-first precedence resolves it silently for
  now; flagging the conflict is a future nice-to-have.
