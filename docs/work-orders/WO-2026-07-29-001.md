# Engineering Work Order — WO-2026-07-29-001

## Problem Statement
PR #8 (WO-2026-07-26-002, Event History Phase 1) merged to `main` at
commit `75856af` with two known correctness defects still open from
Stage 7 round-2 verification, and two ratified scope decisions
(Amendment 2) not yet implemented in code:

1. **DEVICE_RECOVERED false/missed recovery.** In
   `lambda/src/storage/event-history.ts`, the guard
   `ctx.previousState?.offlineCandidate === true && ctx.publishedAt >
   ctx.previousState.lastEventTime` only proves the incoming report is
   *newer* than the last one — it does not confirm the device is
   actually back within the online/offline threshold. A newer-but-still-
   stale report can emit a false recovery event. Separately, because
   `offlineCandidate` is only computed during ingestion, a device that
   goes offline after a normal report was never flagged
   `offlineCandidate: true` in the first place, so its eventual fresh
   report can silently miss emitting recovery at all.
2. **EventHistory sort-key collision.** The sort key
   `{isoTimestamp}#{eventType}#{eventId}` is not fully collision-
   resistant. `eventId` (see `lambda/src/utils/parse.ts`) is derived only
   from deviceId, eventName, timestamp, and S3 key — two different
   payloads sharing those fields produce the same key, and the
   unconditional `PutCommand` silently overwrites the first item. Codex
   reproduced this directly. This breaks the table's core "append-only,
   never modified" guarantee from `docs/architecture/data-model.md`. The
   random-UUID fallback (when `eventId` is absent) avoids collision but
   makes Lambda retries non-idempotent, producing duplicate rows.
3. **Decision 4 not fully implemented.** Amendment 2 to
   WO-2026-07-26-002 ratified the `onSyncFailed` callback in
   `lambda/src/ledger-refresh.ts`, with one required condition: fix the
   declared-but-unawaited `void | Promise<void>` callback type before
   merge. That fix was never made — the type is still loose and the
   caller in `ingestion.ts` still doesn't await it.
4. **Decision 5 not implemented.** Amendment 2 ratified exporting
   `buildAnomalies` from `lambda/src/storage/current-state.ts` (pure
   visibility change) so `event-history.ts` could import the real
   function instead of maintaining a duplicate. `event-history.ts` still
   contains its own `computeAnomalies()`, a ~40-line shadow copy of
   `buildAnomalies()`, unexported and unchanged.

## Operational Impact
EventHistory is new and additive — nothing else in the platform reads
from it yet, so none of the four items above are causing visible harm
today. But the table is being written to in production right now (real
ingestion traffic), so every day this goes unfixed is more data written
under conditions that can produce false DEVICE_RECOVERED events, lose
rows to sort-key collisions, or (for items 3/4) accumulate more code
drift risk before the underlying data has any consumer to sanity-check
it against.

## Approved Architecture / Fix
No new design — this is closing out exactly what Amendment 2 and round-2
verification already specified:
1. `DEVICE_RECOVERED`: tie the trigger to the actual offline-threshold
   evaluation (the same logic `current-state.ts` uses to set
   `offlineCandidate`), not just timestamp ordering — the event should
   only fire when the new report demonstrates the device is genuinely
   back within the expected reporting window.
2. EventHistory sort key: add a collision-resistant component that is
   always present regardless of whether `eventId` exists — e.g. a hash
   of the full event payload, or always generating a random/monotonic
   component rather than only falling back to one when `eventId` is
   missing.
3. `onSyncFailed` callback type: either make it properly awaited end-to-
   end, or narrow the type to synchronous `void` if async was never
   actually intended — resolve the mismatch one way or the other.
4. Export `buildAnomalies` from `current-state.ts`'s existing
   `export { ... }` statement (no logic change). Remove
   `computeAnomalies()` from `event-history.ts` entirely and import/call
   the real `buildAnomalies()` instead.

## Acceptance Criteria
- DEVICE_RECOVERED only fires when the incoming report genuinely
  demonstrates the device is back online per the existing offline-
  threshold logic — not merely a newer timestamp than a stale prior
  report.
- A device that goes offline without ever being flagged
  `offlineCandidate: true` still correctly emits DEVICE_RECOVERED on its
  next report if applicable (i.e., the fix doesn't just narrow the false
  positive without addressing the false negative — or, if closing the
  false negative requires scope beyond this WO, that must be called out
  explicitly rather than left silently unaddressed).
- No two distinct EventHistory writes for the same device can silently
  overwrite each other under the new sort-key scheme, including when
  `eventId` is present and shared across distinct payloads.
- `onSyncFailed`'s type accurately reflects how it's actually invoked
  (awaited if async, synchronous type if not).
- `event-history.ts` no longer contains `computeAnomalies()`; ANOMALY
  events are generated via the real, now-exported `buildAnomalies()`.
- No regression to any of the five event types' existing correct
  behavior (ANOMALY, FIRMWARE_UPDATE, BATTERY_CRITICAL — both already
  verified correct in round 2 — plus LEDGER_SYNC_FAILED).

## Required Tests
- Unit test: DEVICE_RECOVERED does not fire for a newer-but-still-stale
  report.
- Unit test: DEVICE_RECOVERED fires correctly for a genuine recovery.
- Unit test: two distinct payloads with colliding deviceId/eventName/
  timestamp/S3-key (and thus colliding `eventId`) both produce separate,
  non-overwriting EventHistory rows.
- Unit test (or equivalent type-level check): `onSyncFailed` invocation
  is correctly handled per its resolved type.
- Unit test: ANOMALY event output is identical whether produced via the
  old duplicated logic or the newly-imported `buildAnomalies()` (i.e. a
  regression check that the switch didn't change behavior).
- Regression test: existing FIRMWARE_UPDATE, BATTERY_CRITICAL,
  LEDGER_SYNC_FAILED behavior unchanged.
