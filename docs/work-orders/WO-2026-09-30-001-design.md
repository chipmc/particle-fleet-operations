# Design for WO-2026-09-30-001: two API key IDs per consumer during rotation

**Status:** Revision 6, returned to Phase 3 for Chip's review. Open sign-offs remain.
This document does not authorize implementation, deployment, or credential rotation.

**Tracks:** GitHub issue #43. Phase 3 escalations F1-F3/F6 and R3-1/R3-2 from
implementation commit `b316b27` and its review rounds.

## Revision 4 decision

Use published Lambda versions behind one stable `prod` alias, and make every production API
Gateway integration for the shared ingestion/query function invoke that alias. Continue to
derive rotation intent from the bundled registry and key IDs from Lambda environment variables.
Do not weaken the existing configuration checks to tolerate mixed code and environment.

This supersedes the earlier design's assumption that Lambda code and environment variables
become visible together. It does not change the two-slot key lifecycle, the three rotation
deploys, the seven-day alert target, or the decision to defer webhook-secret overlap.

The alias is the deployment boundary:

1. CloudFormation may update `$LATEST` code and configuration in either sequential order.
   `$LATEST` is not traffic-bearing after the one-time alias foundation deploy.
2. CDK publishes an `AWS::Lambda::Version` only after the function update finishes. The
   version is one immutable snapshot containing both the bundled registry and environment.
3. CloudFormation updates the stable `AWS::Lambda::Alias` to that version. Requests may see
   the old or new version around propagation, but no request can see code from one snapshot
   with environment from the other.
4. The old and new snapshots are deliberately transition-compatible at every rotation phase,
   as proved below. The design does not require a globally linearizable cutover.

There is therefore no accepted outage window in this design. Chip is not being asked to sign
off on one.

## Revision 5 decision: checker value safety

Split the checker into a value-erasing API Gateway metadata adapter and a value-free checker
core. The adapter is the only module allowed to import the API Gateway SDK or receive an AWS
response or exception. It performs a runtime projection into closed records containing only
the fields the algorithm needs. The core, alert publisher, logger, and handler receive only
those records or closed failure codes; they never receive a raw SDK response, arbitrary
object, or arbitrary error.

Use a structural output chokepoint as defense in depth, but do not treat it as the primary
proof. A chokepoint alone would merely replace "enumerate output channels" with "enumerate
call sites," so it is insufficient for this escalation. The primary control is absence of the
credential value from every type and runtime value that output-capable code can access.

### Exact guarantee and limitation

This design makes two narrower, testable guarantees:

1. **The approved production adapter requests value-free API Gateway metadata only.** It uses
   only paginated `GetApiKeys` with `includeValues: false`. It does not use `GetApiKey` or
  `GetUsagePlanKeys`; `GetApiKeys` already returns the required `name`, `enabled`, and
  `createdDate`. Its role drops `/apikeys/*` and retains only `GET /apikeys`.
2. **No API key value returned or echoed despite that request can cross the adapter boundary.**
   Runtime projection copies only validated metadata fields. Every upstream exception and
   malformed response becomes a fixed, closed failure code. Unknown properties, error names,
   messages, stacks, causes, request IDs, and metadata are discarded rather than sanitized.

The second guarantee eliminates the unbounded output-channel enumeration problem for the
approved program: once data crosses the adapter boundary, no present or future logger,
warning API, raw stream write, serializer, alert, returned value, or thrown core error can
emit a credential value it never received. Verification therefore targets one ingress
boundary and its dependency direction, not an expanding list of output APIs.

This is not an absolute claim that arbitrary future code running under the checker role can
never read or leak a value. API Gateway IAM does not distinguish `includeValues: false` from
`includeValues: true` on `GET /apikeys`; a future rewrite of the adapter could deliberately or
accidentally request values. TypeScript is not a security sandbox and cannot revoke that AWS
capability. A true IAM-enforced "cannot read" guarantee is unavailable while the checker
obtains API Gateway's authoritative `createdDate` through this API. The design therefore
replaces the old open-ended "never leaks" wording with the two claims above. Code review,
architecture tests, and Phase 5 IAM inspection enforce the first; runtime projection enforces
the second.

That limitation is explicit, not an accepted output-channel gap. If Chip requires an
IAM-enforced inability to read values, this design must stop: a separate architecture would
need a trustworthy value-free metadata source outside API Gateway, and none is established in
this work order. Moving the same API call into another Lambda would only relocate the risk and
is not an acceptable substitute.

### Required module and data boundaries

The implementation may choose names, but it must preserve these ownership boundaries:

- **Metadata adapter:** owns the concrete `APIGatewayClient`, command construction,
  pagination, SDK response decoding, and SDK exception handling. It exports only a capability
  such as `listKeyMetadata(): Promise<KeyMetadataReadResult>`; it does not export a client,
  `send`, command factory, raw response, or raw error.
- **Value-free core:** accepts `readonly KeyMetadata[]`, registry consumers, and time. It owns
  attribution, consistency checks, and overdue-event construction. It has no API Gateway SDK
  import and no output capability.
- **Typed emitters:** accept only `RotationEvent` or `RotationRunSummary`, both built from
  value-free core data. The SNS publisher constructs a `PublishCommand`; the logger constructs
  one structured run summary. Neither accepts `unknown`, `Error`, SDK types, arbitrary
  objects, or pre-serialized strings.
- **Handler:** composes the three capabilities and catches every top-level failure. It may
  throw only a fixed local error code/message after attempted reporting so Lambda's automatic
  error logging cannot serialize an upstream object.

The runtime adapter must compare a response's `name` only with exact slot names derived from
the validated registry. For a match, it constructs a fresh `ObservedKeySlot` containing only:

```text
consumerId: copied from the validated registry, never from the response
slot: locally assigned a or b for the matched registry-derived name
enabled: boolean
createdDate: valid Date/offset-bearing timestamp
```

The adapter does not read, validate, copy, retain, compare, return, or emit the response's
`id`. It also does not return the response's raw `name`; name is used only for exact equality
with locally derived expected names. It must not spread, retain, attach, return, freeze,
stringify, or wrap the source object. A malformed matched item produces a closed
inconsistency/failure code, not a partially copied object. Pagination tokens are
adapter-private and are never logged or returned.

The adapter wraps the complete send/decode loop. Its failure result is a discriminated union
of locally declared codes such as `api_gateway_read_failed` and `invalid_key_metadata`, with
only safe local context needed to classify the run. It must not preserve an upstream `Error`
as `cause`, copy its `name`, `message`, `stack`, `$metadata`, request ID, enumerable fields, or
symbol fields. Character allowlisting is removed because it cannot establish meaning: a
credential can consist entirely of allowed characters.

### Output model

`RotationEvent` remains a closed union of explicit scalar fields and explicit key summaries
(`slot`, enabled). It identifies an overdue secondary by consumer ID and slot, with the
normalized creation date and alert target; it never contains an API Gateway key ID or raw key
name. `RotationRunSummary` contains only locally computed counts, registry consumer IDs, and
closed reason codes. Serialization occurs inside the typed SNS/log adapters from those
records. No generic "sanitize then stringify," object spread, error formatter, or recursive
error traversal belongs on the path.

This output chokepoint is useful because it makes accidental output easy to review, but it is
not sufficient by itself. The design remains safe if another output channel is later added to
the core/handler side because that side has only value-free records. Adding output inside the
metadata adapter, exposing raw adapter data, or importing the API Gateway SDK outside the
adapter is an architecture violation requiring a new review.

### Failure behavior

Metadata-read or decode failure must never become a quiet healthy run. The handler publishes a
fixed value-free checker-failure event when SNS is available, logs a fixed typed summary, and
fails with a fixed local error so the existing Errors alarm fires. Per-consumer malformed
deployed metadata remains an inconsistency when it can be attributed safely; a failed page
read that makes completeness unknowable fails the whole run.

Publish failures are also reduced to fixed local codes. The checker may continue attempting
other already-built value-free events, then fail once. No upstream SNS error object or text is
retained. This preserves alert-only behavior, no retries, and no deploy blocking.
"No retries" applies to SNS publish calls specifically (each alert is attempted once,
`maxAttempts: 1`), not to the adapter's idempotent `GetApiKeys` metadata reads, which keep the
SDK's default retries because a retried read cannot duplicate an alert.

### Alternatives rejected

- **Channel interception or blocking:** rejected. The review history proves the set is open
  ended (`console.dir`, warnings, streams, serializers, and error causes were successive
  misses). More interception only narrows the same enumeration problem.
- **Output chokepoint alone:** rejected as the guarantee. It still requires proving every path
  uses the chokepoint and leaves raw data available elsewhere in the process.
- **Type-only records over raw objects:** rejected. A TypeScript assertion or interface does
  not remove runtime properties. A fresh runtime projection is mandatory.
- **Sanitized upstream error details:** rejected. Allowed syntax does not prove safe meaning.
  Error name and request ID are not needed for the checker contract and are discarded.
- **Separate reader Lambda with the same API permission:** rejected. It relocates rather than
  removes the value-capable principal and creates another output/error boundary to secure.
- **IAM as the primary control:** unavailable. Resource scoping can remove unrelated API
  Gateway operations and `/apikeys/*`, but cannot constrain `includeValues` on `/apikeys`.

### Revision 5 implementation verification

The implementation is separate. In addition to all retained Revision 1-4 fixtures, require:

- Only the metadata-adapter module imports `@aws-sdk/client-api-gateway`. The checker core,
  event constructors, emitters, and handler composition expose no generic `send`, SDK type,
  raw response, `unknown` payload, or `Error` parameter across their public boundaries.
- The adapter issues only `GetApiKeysCommand` with the literal `includeValues: false`, handles
  opaque pagination, and never issues `GetApiKey` or `GetUsagePlanKeys`. Synthesis grants only
  `apigateway:GET` on `/apikeys`, not `/apikeys/*` or `/usageplans/*`.
- Feed the adapter hostile successful pages containing a sentinel credential in `value`,
  `id`, and unmatched `name`, plus nested unknown fields, enumerable fields, non-enumerable
  fields, getters, and symbols. Its exact output must equal freshly constructed slot records
  whose consumer ID and slot come from registry-derived expectations. Neither `id` nor raw
  `name` may cross the boundary. A getter for an unapproved property must not be evaluated.
- Feed failures with the sentinel in `name`, `message`, `stack`, `cause` chains, request IDs,
  `$metadata`, enumerable properties, non-enumerable properties, and symbols. The exact result,
  alert, log record, returned value, and final thrown error must contain only fixed local codes
  and approved local context. Do not prove this by spying on an enumerated list of output
  channels; prove the exact values crossing each architectural boundary.
- Compile-time negative fixtures must reject adding `value` or raw SDK/error fields to
  `ObservedKeySlot`, `RotationEvent`, `RotationRunSummary`, adapter failure results, and
  emitter inputs. They must also reject `id` and raw `name` on every boundary/output type.
  Runtime tests remain authoritative because TypeScript alone does not strip fields.
- An architecture test fails if an API Gateway SDK import appears outside the adapter, if the
  adapter exports a client/raw send capability, or if output/SNS dependencies enter the
  adapter. This is a finite module-boundary rule, not output-channel enumeration.
- Make every registered consumer independently reportable in the production-handler fixture,
  with a unique expected inconsistency/event for each, and assert the exact consumer-ID set
  and count. A handler that skips any consumer must fail.
- From a real synthesized cloud assembly, assert the checker Lambda's exact runtime and
  configured handler. Execute that configured export from the synthesized asset with the
  production registry and controlled adapter/publisher boundaries; assert all consumers are
  evaluated and the expected value-free records are emitted. Merely finding a function export
  is insufficient.
- Inspect the whole synthesized template for policies and resource-based permissions referring
  to the checker role by `Ref`, ARN, `Fn::GetAtt`, role name/token, or principal, and assert an
  explicit allowlist. Phase 5 must also inspect the deployed role's managed/inline policies,
  permissions boundary, and relevant resource policies with IAM tooling. Record this as
  defense in depth, not proof that API key values are unreadable.
- Keep a negative-control test showing the role/API model permits `includeValues: true`; the
  test must document why the guarantee depends on the reviewed adapter command and boundary,
  not falsely attribute that guarantee to IAM.

## Revision 6 decisions: R3-1 and R3-2

### R3-1: remove key ID from the checker boundary

**Chosen fix:** use neither a length/shape policy nor key-ID provenance. Remove API Gateway
`id` from the checker's value-free model and every checker output. The checker does not need an
ID to count exact slot names, determine enabled state, anchor the clock to `createdDate`, or
identify a consumer and slot in an alert.

AWS documents `ApiKey.id` only as a `String`, with no length, character-set, or format
constraint. Its `GetApiKey` example uses a 42-character alphanumeric ID, and the deprecated
`generateDistinctId` input expressly controlled whether ID and value were distinct. No
replacement guarantee is documented. Therefore this design makes no claim that a key ID has a
safe shape or is necessarily distinct from a key value. It imposes no application length
threshold and does not emit an ID merely because it matches a CDK-provided ID: provenance
would show ownership, but it would not prove that the byte string is not also a credential.

The adapter receives raw SDK items because that is unavoidable at the AWS boundary. For each
registry-derived slot name, it emits zero or more fresh `ObservedKeySlot` records labeled with
the local consumer ID and slot. It reads only `name`, `enabled`, and `createdDate`; `id` and
`value` are ignored even when present. Duplicate exact names remain detectable by record count.
Unknown names are ignored without being copied or reported. Malformed data is reported with a
fixed local reason and registry-derived consumer/slot when attribution is safe.

This structurally closes R3-1: no arbitrary API Gateway identifier crosses into the checker
core, alerts, logs, return values, or thrown errors. Operators still record and distinguish
key IDs through the existing value-safe CLI queries and API Gateway access logs during the
rotation procedure. That operational responsibility does not require the scheduled checker to
repeat IDs in its output.

- <https://docs.aws.amazon.com/apigateway/latest/api/API_GetApiKey.html>

### R3-2: retained bare-function rollback guards

R3-2's retained-guard mechanism was removed (2026-10-03) — AWS fleet-ops is a diagnostic copy, not a system of record, so the brief rollback gap this mechanism existed to prevent is an accepted, documented operational cost instead. See docs/operations/wo-2026-09-30-001-foundation-rollback-drill.md for the manual rollback procedure.

### Revision 6 implementation verification

- Hostile `GetApiKeys` pages put credential sentinels separately in `id`, `value`, and raw
  `name`, including strings that satisfy any previously proposed ID regex. Assert exact
  adapter, core, event, log, return, SNS, and fixed-error boundary values contain no `id`, raw
  `name`, or sentinel. Do not assert an ID length or character pattern anywhere.
- Assert overdue and inconsistency events identify keys only by registry consumer ID and slot.
  Duplicate exact slot names remain an ambiguity inconsistency without emitting either raw ID.
- Compile-time and architecture fixtures reject `id` and raw `name` in `ObservedKeySlot`,
  events, summaries, emitters, and errors. The adapter is the only code allowed to access the
  raw response's `name`; no checker code accesses raw `id`.
- Foundation synthesis contains alias-qualified active permissions plus the complete set of
  unqualified rollback guards. Each guard is route-scoped, wildcard-stage, account-scoped, and
  has both retain policies. Tests must distinguish dormant permissions from integrations and
  continue to fail if any production trigger targets the unqualified function.
- Compare the pre-foundation and foundation templates in both update directions. Model removal
  of guard resources using CloudFormation `Retain`, and verify every old HTTP/REST integration
  has a matching retained permission before it can target the bare function. Specifically
  cover the REST deployment/stage ordering that produced R3-2.
- A rollback drill in a non-production stack must deploy foundation, deploy the old template,
  verify retained statements with `GetPolicy`, and smoke-test every route throughout the
  transition. Repository synthesis cannot certify retained runtime policy state.
- Test cleanup and re-foundation procedures against retained statement-ID conflicts before
  authorizing either operation in production.

The AWS CloudFormation `AWS::Lambda::Function` reference states that CloudFormation calls
`UpdateFunctionConfiguration` and `UpdateFunctionCode` sequentially, invocations can occur

documentation defines an alias as an updateable pointer to a function version, and
`AWS::Lambda::Alias.FunctionVersion` updates without interruption.

## Why the other options are rejected

### Environment variables as the only declaration source

Not selected. Inferring rotation solely from the presence of generated key-ID variables would
close these four cases, but it would remove explicit lifecycle intent from the registry while
the CDK resources, disable phase, checker, and cleanup procedure still need that intent. It
also addresses only this particular code/config dependency; future coupled code and
configuration changes on the shared function would retain the same deployment hazard.

The registry remains the source of lifecycle intent. Environment variables remain the source
of generated physical IDs that cannot exist in the static registry. A version binds both into
one invocable snapshot without pretending they are the same kind of data.

### Tolerating mixed states in authentication

Not selected. An invocation cannot reliably distinguish a transient CloudFormation interval
from a persistent malformed deployment. Accepting either mixed state would weaken a useful
configuration invariant, could keep an undeclared key authorized, and would still require
special behavior for every future code/config transition. The existing consumer-scoped 503
checks stay strict and testable; mixed snapshots are kept away from traffic instead.

## Scope retained from Revision 3

Implement API key overlap now and defer webhook-secret overlap to a separate architecture
review. Each consumer has stable CDK key slots `a` and `b`, but only its primary slot exists
normally. During rotation the registry declares the other slot as secondary and selects phase
`overlap` or `old-disabled`.

The registry schema contains lifecycle metadata only:

```json
{
  "apiKey": {
    "primarySlot": "a",
    "rotation": {
      "secondarySlot": "b",
      "phase": "overlap"
    }
  }
}
```

It contains no key IDs, key values, or timestamps. API Gateway assigns IDs after resource
creation. The daily checker uses API Gateway metadata, with `includeValues: false`, to read the
secondary key's `createdDate`. Seven days (168 hours) is an alert and human-review target, not
a validity cutoff or deploy gate. Deploys remain plain `cdk deploy` and nothing automatically
disables, deletes, or rejects a key because of age.

## Alias foundation deploy

This is a one-time prerequisite and must complete before the two-key mechanism rollout or any
rotation. Keep it behavior-neutral: do not combine it with a registry schema change, key
creation, credential change, or unrelated Lambda code/configuration change.

The design requires:

- one published version of the current shared function snapshot;
- one stable alias named `prod` pointing to that version;
- every REST API and HTTP API production integration that currently targets
  `ingestionFunction` changed to target the alias;
- API Gateway invoke permission scoped/generated for the qualified alias target; and
- no direct production event source or API integration left invoking the unqualified function
  or `$LATEST`.

Revision 6 additionally requires dormant, route-scoped bare-function rollback permissions.
Those permissions do not relax the last bullet: they authorize a possible old-template
retarget, but no foundation integration or trigger uses them.

Phase 5 must inspect the synthesized template, not rely on construct intent. The version must
depend on the complete function resource update. Each API integration must contain the
qualified alias ARN, and its deployment/stage update must depend on usable alias invocation
permission. A direct-invocation search is a release gate for this foundation deploy.

Expected `cdk diff`: one `AWS::Lambda::Version`, one `AWS::Lambda::Alias`, qualified Lambda
permissions, retained route-scoped bare-function rollback guards, and API Gateway
integration/deployment changes needed to replace the unqualified target with the alias. It
must show no API key, usage plan, secret, registry, function IAM, function code, or function
environment change.

After deployment, smoke-test every route served by the shared function, including the legacy
ingestion route, all query/fleet routes, and the REST ingestion route. Confirm CloudWatch
invocation records identify the published version rather than `$LATEST`. Rollback restores the
old API integrations; the function snapshot itself is unchanged, so this foundation rollback
does not create a code/config mismatch.

## Mechanism rollout

After the alias foundation is verified, deploy schema version 2, stable key slots, strict
consumer-scoped configuration checks, the daily checker, notifications, and tests with every
existing consumer on primary slot `a` and no declared rotation.

The function update now occurs off the request path. CloudFormation publishes the resulting
complete snapshot and moves `prod` only after publication. Confirm no existing `ApiKey`,
`UsagePlan`, or `UsagePlanKey` is replaced or deleted and no ingestion-function IAM permission
is broadened. Verify existing traffic by key ID after the alias moves.

## Rotation sequence and ordering proof

### Deploy 1: create overlap

Declare the other slot as secondary in phase `overlap`. The diff must add one `ApiKey`, one
`UsagePlanKey`, and the secondary ID environment variable, publish a new function version, and
move `prod` to it. It must not replace or mutate the old key or usage plan.

Do not give the new key value to any client until the stack is `UPDATE_COMPLETE` and both the
usage-plan association and alias target are verified.

| Observable state during deploy | Live old key | Result |
|---|---|---|
| Old alias target, before or after new key creation | primary in steady snapshot | 200 |
| New alias target | primary in complete overlap snapshot | 200 |

The new key is not yet distributed while ordering is unsettled. After completion, verify both
key IDs with the same consumer secret, then migrate clients one at a time. Observe zero old-key
requests for at least 24 hours or longer than the least frequent publisher interval.

If deploy 1 fails, CloudFormation can move the alias back to the old version and remove the new
key. The old key remains valid in both snapshots. Do not distribute the new value after a
failed or rolled-back stack update.

### Deploy 2: disable the old key

After the zero-use gate, change phase to `old-disabled`. The diff must change only the old
key's `Enabled` state among key resources, publish the complete phase snapshot, and move the
alias. Both snapshots map both IDs to the same consumer, so alias and key-disable ordering is
safe:

| Observable state during deploy | Result |
|---|---|
| Old overlap snapshot, old key still enabled | both keys accepted |
| New old-disabled snapshot, old key still enabled | both IDs still map; both accepted |
| Either snapshot after old key is disabled | old rejected by API Gateway; new accepted |

Observe for at least 24 hours. Reverting phase to `overlap` and re-enabling the same old key is
the reviewed rollback. It does not reset the secondary key's `createdDate`.

### Deploy 3: delete old and promote new

Set `primarySlot` to the retained secondary slot and remove `rotation`. The diff must delete
only the old `ApiKey` and its `UsagePlanKey`, change the primary environment variable to the
retained key ID, remove the secondary variable, publish the cleanup snapshot, and move the
alias. It must retain the new key and usage plan without replacement.

| Observable state during deploy | Live new key | Result |
|---|---|---|
| Old alias target | secondary in old-disabled snapshot | 200 |
| New alias target | primary in complete steady snapshot | 200 |

The old key was disabled and passed the observation gate before this deploy, so deleting it in
parallel cannot interrupt a valid client. If rollback occurs after physical deletion,
CloudFormation may recreate that slot with a different key value; rollback must be judged by
continued new-key service, not by recoverability of the old physical credential.

After completion, verify new-key traffic, absence of the old key, one-key checker state, and
the alias's exact published version. A later rotation recreates the free opposite slot.

## Logging and operational bounds

Record exact old and new key IDs at deploy 1. Access logs and `ingestion_auth` entries use
those IDs to distinguish traffic. Never output key values, secret values, prefixes, or hashes.
The operator-only clipboard command in the runbook remains outside agent sessions and logs.

At first disablement, verify whether a disabled-key 403 records the old ID or `"-"`. If it is
`"-"`, treat such 403s as ambiguous and correlate by request ID, time, source IP, and client
delivery evidence. This does not weaken the pre-disable zero-use gate.

The checker continues daily overdue alerts while two keys exist, including `old-disabled`,
until deploy 3 leaves one. Checker failure triggers its own alarm. Nothing blocks deployment;
after an overdue alert, Chip decides whether to resume, roll back, or clean up.
