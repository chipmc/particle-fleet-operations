# Design for WO-2026-09-30-001: two API key IDs per consumer during rotation

**Status:** Revised for Chip's review; open sign-offs remain. This document does not
authorize implementation or credential rotation.

**Tracks:** GitHub issue #43.

## Outcome

Implement API key overlap now and defer webhook-secret overlap to a separate architecture
review. Each consumer gets two stable CDK key slots, `a` and `b`, but only its primary slot
exists normally. During rotation, the registry temporarily declares the other slot. Both key
IDs resolve to the same consumer until the old key is disabled and eventually removed by
deployment. A seven-day target measured from the new key's creation triggers a recurring
operator alert, **not** an automatic cutoff or deploy block: a late migration must not
become an outage.

This is the smallest change that unblocks API key rotation. It preserves the API key/secret
pair check and does not change secret loading, secret comparison, or Lambda IAM permissions.

**Classification:** additive, behavior-changing, contract-changing, security-sensitive, and
infrastructure-sensitive. It is not refactor-only.

## 1. Scope: API keys now; secret overlap later

**Answer:** API key overlap is worth implementing independently. Defer secret overlap.

Keys and secrets share the operational need for a bounded overlap, but they do not share an
implementation:

- API Gateway owns API key validation. CDK must create two `ApiKey` resources and attach both
  to one usage plan; the Lambda only needs a many-key-to-one-consumer ID mapping.
- Secrets Manager owns secret versions. Supporting secret overlap would require selecting
  version stages or IDs, caching multiple secret values, comparing every candidate, and
  distinguishing two matches for one consumer from one match for each of two consumers.

Combining them would broaden a targeted key-rotation fix into secret-version and
constant-time-auth redesign. API key overlap immediately unblocks the runbook and the
deferred key rotation while leaving the existing secret contract unchanged.

The key design must not constrain a later secret design:

- Key resolution remains separate from secret matching; it returns either a consumer ID, a
  consumer-scoped configuration error, or unknown.
- Secret matching continues to resolve independently from a presented secret to a consumer.
- The final equality check between those consumer IDs remains the authorization decision.
- The new registry fields are under `apiKey`; a future design can add separate
  `secretRotation` metadata without overloading key lifecycle state.
- A future secret-overlap design must cache a list of candidates per consumer, compare all
  candidates without early exit, and deduplicate matches by consumer ID before applying
  cross-consumer duplicate detection.

## 2. Declaring the second credential

**Answer:** The registry declares which key resources CDK creates and which key is primary;
CDK identifies the resources. API key IDs do not go in the registry.

### Registry schema

Increment the registry to schema version 2. Every consumer gets an explicit primary slot:

```json
{
  "apiKey": {
    "primarySlot": "a"
  }
}
```

During a rotation, that consumer temporarily declares:

```json
{
  "apiKey": {
    "primarySlot": "a",
    "rotation": {
      "secondarySlot": "b",
      "phase": "overlap"
    }
  }
}
```

Allowed slots are `a` and `b`. `secondarySlot` must differ from `primarySlot`. Allowed phases
are `overlap` and `old-disabled`. Rotation is valid only for an active consumer. Do not put
`startedAt` or `expiresAt` in the registry: it is bundled into the Lambda at build time and
cannot know when a later deployment actually created the new key. Validation rejects malformed fields
at synth, including extra timestamp/deadline fields; it does not reject an overdue rotation
merely because time has passed. Also reject registries whose generated slot names collide
across consumers (for example, consumer `alpha` slot `b` and consumer `alpha-b` slot `a`);
the checker cannot attribute two owners to one name.

The registry contains identifiers and lifecycle metadata only. It contains neither an API key
value nor an API key ID. Its `apiKey.rotation` block is **not** a deployed intent parameter:
it is required CDK input to create the second key and later disable the old one, and stays
through deploy 2. The checker uses observed key count, not this declaration, to decide
whether rotation is still in progress.

### Stable CDK resources

Slot `a` must retain the existing construct and CloudFormation logical identity:

`IngestionConsumer<ConsumerPascalId>ApiKey`

This is mandatory so deploying the mechanism does not replace today's key. Slot `b` gets a
new, stable construct identity:

`IngestionConsumer<ConsumerPascalId>ApiKeyB`

Outside rotation, CDK creates only `primarySlot`. During rotation, it also creates
`secondarySlot` and attaches it to the existing usage plan. On later rotations the slots
alternate. Promoting slot `b` means retaining its resource and deleting slot `a`, not
renaming `b` to `a`. A subsequent rotation recreates slot `a` as a new physical key while
leaving slot `b` untouched.

The existing slot `a` API key name remains unchanged. Slot `b` uses a distinct name ending in
`-b`. The checker uses exact names to discover keys; key IDs are the authority in logs
and traffic checks.

### Lambda environment and lookup

Preserve the existing primary environment variable:

`INGESTION_API_KEY_ID_<CONSUMER_ID>`

During rotation, add:

- `INGESTION_API_KEY_ROTATION_ID_<CONSUMER_ID>` for the secondary key ID.

The primary variable points to whichever stable slot the registry names as primary. Keeping
its name avoids changing the no-rotation path. Key IDs are non-secret configuration;
no credential value enters the environment. There is **no** deadline
environment variable and no deadline-based rejection in the Lambda. In `old-disabled`,
retain both ID mappings until deploy 3; API Gateway, not the Lambda clock, rejects the
disabled key.

Today `buildApiKeyConsumerLookup` returns `string | undefined`
(`lambda/src/consumer-auth.ts:140-151`). Replace that with a tagged result for each supplied
ID: `consumer(consumerId)`, `config-error(consumerId)`, or `unknown`. Build the map for each
consumer independently. Validate its expected primary and (if rotation is declared)
secondary ID configuration; if malformed, map **that consumer's known ID(s)** to its
`config-error` result and log a structured error with its consumer ID and reason, never a
credential value. Do not throw for all consumers or discard the whole map. An unprovided
secondary ID cannot be recognized as belonging to any consumer; the known primary still
reports the error, while an unknown ID stays unknown. Reject duplicate IDs across consumers
as configuration affecting the colliding IDs; never resolve one by registry order. Schema
errors found before deployment still fail synth.

`validateConsumerRequest` must consume the tagged lookup result after secret loading and
**all** candidate hashes/comparisons (`consumer-auth.ts:99-108`), even for an unknown or
misconfigured key. A known key tagged `config-error` yields
`credential_config_unavailable` and a consumer-scoped error log, then
`handleIngestion` (`lambda/src/ingestion.ts:57-66`) returns 503 via its existing response
mapping. A valid key for another consumer still succeeds with its own secret; its
cross-consumer pairings still fail 401. Unknown IDs retain the existing mismatch behavior;
missing secrets retain the existing fast-fail path. A Secrets Manager failure or duplicate
secret is a separate, existing configuration failure and is not claimed to be
consumer-isolated. **Malformed rotation configuration for one consumer yields 503 for that
consumer only, never for any other consumer.**

## 3. Bounding the overlap window

**Answer:** Seven days (168 hours) is an **alert/escalation target**, not a validity limit.
The target covers one-at-a-time client edits, at least 24 hours of zero old-key use, and
24 hours of disabled-key observation. A "maximum" enforced by rejection would create the
unplanned outage this work order prevents. Chip must approve the target and the policy for
overdue rotations; the old key stays usable past the target while phase is `overlap`.

The clock starts at the **secondary key's API Gateway `createdDate`**, when its resource
is created during deploy 1. If deploy 1 rolls back, that key is deleted; creation is an
observable event, not a declared intention. This is minutes before the stack reaches
`UPDATE_COMPLETE`, an immaterial difference for a seven-day alert target. Read the key by
ID using `GetApiKey` with `includeValue: false`; parse the UTC-offset timestamp as an
instant at second precision, then add 168 hours. Never infer the start from a registry
edit, deploy start, `lastUpdatedDate`, or the time a checker runs. If the secondary
physical key is ever re-created, its new `createdDate` starts the target for that *new*
key; it does not preserve the original key's start. The operator must review that
replacement, record the new ID, and re-verify client migration before treating it as a
fresh rotation. The checker has no historical anchor and cannot detect an unrecorded
replacement of the same-named key by itself.

The mechanism rollout installs a daily EventBridge-scheduled checker and a dedicated
rotation SNS topic with a Chip email subscription. At **09:00 UTC daily**, the checker
paginates `GetApiKeys` with `includeValues: false` and matches **exact** CDK-managed
names: `particle-ingestion-<consumer-id>` for slot `a` and
`particle-ingestion-<consumer-id>-b` for slot `b`. Derive these names from every
registered consumer, comparing the full name for equality, never a substring or prefix;
`particle-ingestion-alpha` must not match `particle-ingestion-alpha-b` or
`particle-ingestion-alpha-long`. Registry validation prevents two consumers from owning
the same generated slot name; the current CDK naming convention is sufficient for
attributing its managed keys without a new tag or mutation of today's key. If the
deployed API lists duplicate names or otherwise ambiguous matches, alert rather than
guess. This identifies managed resources by name, not by usage-plan association:
`GetUsagePlanKeys` returns key values and must **not** be used by the checker. Explicitly
exclude key values from every request, response, alert, and log.

Use the deployed checker bundle's registry of consumers and slots, updated with each
rotation deploy, to derive names and report phase; do not use its `rotation` block as
proof that a second key exists. **Two distinct keys existing** for a consumer means
rotation is in progress, whether both are enabled (`overlap`) or one is enabled and
one is disabled (`old-disabled`).
One key means no observed rotation; zero or more than two, or a declared rotation with
only one key, is an inconsistency to alert on, not a reason to silently conclude that
migration succeeded. A two-key state without a registry rotation block also remains
unfinished and warrants an inconsistency alert. For two keys, use `GetApiKey` with
`includeValue: false` to read the declared secondary slot's `createdDate`, even if
the old key is disabled; that slot must have been created after the primary, or the
checker reports an inconsistency. If the registry no longer declares rotation despite
two keys still existing, report that inconsistency and use the newer key's `createdDate`
for the overdue alert. A missing/unparseable date or ambiguous key attribution must
produce a checker error/alert, never a false healthy result. No SSM anchor or
rotation-intent parameter is needed.

On the first daily run at or after `createdDate + 168 hours` (up to 24 hours after the
threshold), and on each later daily run while two keys exist, the checker publishes one
structured `ingestion_api_key_rotation_overdue` event **per consumer per daily run**
(consumer ID, phase if declared, secondary key ID and creation time, days overdue, no key
value) to that SNS topic, delivered to `chip@seeinsights.com`. A successful deploy 3
leaves one key, stopping overdue alerts only once the checker observes that state.
Checker execution/publish failures must surface through its CloudWatch Errors alarm to
the same topic, not silently suppress overdue notices. Its own IAM is narrowly scoped
to read-only API Gateway key metadata and SNS publish on this topic; it does not change
the ingestion Lambda's IAM or authorization clock. SNS subscription confirmation and
delivery must be checked in Phase 5. This is **new infrastructure and a new notification
channel** requiring Chip's sign-off; the existing SNS email topic is for monthly archives
(`infra/lib/infra-stack.ts:187-190`) and is not silently repurposed.

**Deploys remain plain `cdk deploy`** (`docs/operations.md:59`). There is no change-set
guard, pre-execution guard, mandatory deploy entry point, or wrapper. This deliberately
narrows decision 4's literal wording, as directed by Chip: never blocking an unrelated
deploy was the goal; with no deploy wrapper in place, blocking **no** deploy over a stale
rotation is the simpler guarantee. The daily alert keeps a forgotten rotation from
running unnoticed. Synth checks registry shape, not age. After the seven-day target is
missed and the alert fires, **resuming, rolling back, or cleaning up** the rotation
requires a human decision by Chip, not an automatic action. Nothing acts on the
deadline except the alert. The rotation issue stays open until deploy 3 and the
one-key state are verified.

## 4. Completing a rotation

**Answer:** Use one mechanism rollout followed by three rotation deploys. The old key is
disabled before it is deleted, and its ID leaves the Lambda mapping only when deleted.

### One-time mechanism rollout

Before rotating any credential:

1. Implement schema version 2, the two stable CDK slots, the optional secondary environment
   variable, consumer-scoped lookup errors, scheduled checker, notifications, and tests.
2. Set every existing consumer's `primarySlot` to `a`; declare no rotation.
3. Confirm `cdk diff` shows the Lambda code/configuration update required by the mechanism
   and bundled registry plus the approved monitoring/notification infrastructure, but no
   ingestion `ApiKey`, `UsagePlan`, or `UsagePlanKey` replacement or deletion and no
   **ingestion Lambda** IAM change. The checker has its own narrowly scoped permissions.
4. Deploy, confirm the SNS email subscription, and verify existing traffic remains
   successful by current key ID.

The exact deployed-resource comparison cannot be certified from repository source. The AWS
Agent must verify this diff against the deployed stack before Chip approves deployment.

### Deploy 1: create overlap

1. Add the target consumer's `rotation` object with the other slot and phase `overlap`.
2. Confirm `cdk diff` shows:
   - one new `ApiKey`;
   - one new `UsagePlanKey` attaching it to the existing usage plan;
   - a Lambda environment addition for the secondary ID; and
   - a Lambda asset/configuration change because the registry is bundled into the Lambda
     (and a checker bundle update if needed for its consumer/phase metadata).
3. Confirm the diff shows no replacement or mutation of the old key, no usage-plan
   replacement, no secret change, and no ingestion Lambda IAM change.
4. Deploy, then record the old and new key IDs and the new key's `createdDate` using
   output restricted to non-sensitive fields (`id`, `name`, `enabled`, `createdDate`).
   Confirm both key resources and the new usage-plan association exist before migration;
   stop and investigate if the second key or its creation time cannot be verified.
5. Check that the new key's `createdDate` is parseable with its UTC offset; it, not
   stack completion, starts the seven-day alert target.
6. Verify requests authenticated by each key ID succeed with the same consumer's existing
   webhook secret. Do not rotate the secret.

### Client migration and verification

Only the operator transfers the new key value to each client, in their own terminal/UI,
without displaying, logging, or pasting it into an agent session. This design prescribes
**no automated or agent-run command** that prints a credential value; it does not prohibit
the existing runbook's deliberately manual, operator-only
`aws apigateway get-api-key --include-value --query value --output text | pbcopy` step
(`docs/security/webhook-secret-rotation-runbook.md:152-158`). Never run that command in
an agent session or shared/logged terminal.

Update one client at a time. After each update:

- confirm access-log entries use the new key ID and return 200;
- confirm matching `ingestion_auth` entries report `success` for the expected consumer and
  new key ID; and
- confirm that client's events continue to arrive.

After the last client update, observe for at least 24 hours, or longer than the least
frequent expected publisher interval. The old key ID must have zero requests before deploy
2.

### Deploy 2: disable the old key

1. Only after the zero-use gate, change phase from `overlap` to `old-disabled`.
2. Confirm `cdk diff` shows the old primary `ApiKey` changing from enabled to disabled and
   the bundled-registry Lambda asset/configuration change (and checker bundle update for
   phase metadata).
3. Confirm both key resources and both `UsagePlanKey` associations remain, both key IDs
   remain in the Lambda environment, and ingestion Lambda IAM is unchanged.
4. Deploy and observe for at least 24 hours.

Any missed old-key client now receives 403 from API Gateway, before Lambda invocation. Its
403 access-log `apiKeyId` **might** be the real old key ID; this is **verify at first use**,
not an established API Gateway behavior. Per Chip's review data, last week's
missing/invalid-key 403s logged
`apiKeyId` as `"-"`. There is no corresponding `ingestion_auth` entry for a Gateway
rejection. During the first disablement, make a controlled operator-side request with the
disabled key (without exposing its value to an agent or log), correlate its request ID,
time, source IP, path and 403 status (and response request ID if available) to the
access log, and verify whether `apiKeyId` is the old ID or `"-"`. If it is `"-"`,
treat **all** 403s with `apiKeyId: "-"` on
the route as ambiguous, not proof that the old key was used. Triangulate a missed client
from its own delivery logs, time/source IP and request ID when available; if attribution or
recovery is uncertain, re-enable the old key by reviewed rollback while investigating. The
pre-disable zero-use gate still protects the rotation regardless of that marker. A rollback
to `overlap` with the same secondary key does not reset its `createdDate`; after the
seven-day alert target, it requires explicit Chip review, not a fictitious extension.

### Deploy 3: delete the old key and promote the new slot

1. Set `primarySlot` to the former secondary slot and remove `rotation`.
2. Confirm `cdk diff` shows:
   - deletion of the old `ApiKey`;
   - deletion of only the old `UsagePlanKey`;
   - retention, without replacement, of the new key and usage plan;
   - the primary environment variable changing to the retained key ID;
   - removal of the rotation ID environment variable; and
   - the bundled-registry Lambda asset/configuration change (and checker bundle update).
3. Confirm there is no secret or ingestion Lambda IAM change. A cleanup deploy is not
   automatically blocked if the alert target was exceeded; Chip decides whether to
   proceed after review.
4. Deploy and verify new-key traffic remains successful and the old key is gone. Confirm
   the checker observes one key and stops overdue alerts, not merely a registry edit.

After deploy 3, the old physical key cannot be re-enabled. A later rotation uses the now-free
opposite slot and repeats the same sequence.

## 5. Distinguishing the keys in logs

**Answer:** Use exact key IDs recorded at deploy 1. No new credential data needs to be logged.

Current `ingestion_auth` success and failure entries already include `apiKeyId`
(`lambda/src/ingestion.ts:59-63`). Current REST API access logs already include `apiKeyId`
(`infra/lib/infra-stack.ts:695`). The old and new resources have different API Gateway key
IDs, so their traffic is distinguishable throughout overlap.

The runbook must label the two recorded IDs as `oldKeyId` and `newKeyId`, then:

- group or filter access logs by exact `apiKeyId` to measure use and status for both keys;
- correlate Lambda-invoked requests with `ingestion_auth` by exact key ID;
- treat an old-key access-log count of zero over the required observation interval as the
  migration gate; and
- at first disablement, **verify at first use** whether a 403 from the disabled key logs
  its ID or `"-"`; if `"-"`, do not attribute ambiguous 403s by key ID. Use request
  ID/time/source IP, client delivery evidence, and rollback if necessary. This observation
  does not change the pre-disable zero-use gate.

The six Particle webhooks still share one API key, so neither log can identify which of those
six used it. The safe procedure remains one-at-a-time client updates followed by a zero-use
window for the old key.

All documented checks must select or display IDs, names, enabled state, counts, timestamps,
and statuses only. They must never output API key values, secret values, value prefixes, or
hashes.

## Constraint preservation

| Constraint | How the design preserves it |
|---|---|
| Pair check | Both key IDs map to the same consumer ID, then the existing equality check at `consumer-auth.ts:122-126` compares that ID with the independently matched secret consumer. A key for consumer A cannot pair with consumer B's secret. |
| Constant-time secret comparison | Secret loading and the all-candidate hash/`timingSafeEqual` loop at `consumer-auth.ts:99-108` are unchanged. Key lookup occurs independently after secret matching. |
| Duplicate-secret detection | Secret candidates remain one value per consumer, so the cross-consumer check at `consumer-auth.ts:113-119` is unchanged. A later secret-overlap design must deduplicate matches by consumer before checking for multiple distinct consumers. |
| No secret values in environment variables | Only a secondary API key ID is added. `GetSecretValue` continues to load secret values at runtime. |
| No rotation by resource rename | Stable `a` and `b` construct identities alternate. Promotion changes registry selection while retaining the new resource's logical identity. |
| No credentials printed in output | Automated and agent-run checks use IDs and non-sensitive fields only. The existing runbook's manual `--include-value`-to-`pbcopy` transfer is operator-only, never agent-run or logged. |

## Required implementation verification

Implementation is a separate work order. Its tests must use these reviewer-specified
fixtures:

- Consumers `alpha` and `beta`; `alpha` has key IDs `alpha-a` and `alpha-b`, while `beta`
  has `beta-a`.
- In `overlap`, `alpha-a` and `alpha-b` each succeed with alpha's secret; `beta-a` succeeds
  with beta's secret. Every cross-consumer key/secret pairing fails 401. At exactly one
  millisecond before, exactly at, and one millisecond after
  `alpha-b createdDate + 168 hours`, **both** alpha keys still resolve to alpha; the
  Lambda does not reject by clock. During `old-disabled`, both IDs remain mapped in the
  Lambda, but API Gateway rejects `alpha-a` with 403 before invocation.
- A malformed alpha rotation (e.g. missing secondary ID, invalid slot, or malformed
  rotation metadata) yields `credential_config_unavailable`/503 for **alpha's known
  key ID only**, while `beta-a` plus beta's secret still returns 200; `beta-a` plus
  alpha's secret remains 401. Unknown IDs remain 401, not a global 503. Assert the
  consumer-scoped configuration log identifies alpha without a credential value.
- The same key ID assigned to two consumers is rejected as configuration for those IDs,
  not resolved by registry order; an unrelated third consumer still succeeds.
- Instrument digest/`timingSafeEqual` calls: for alpha and beta, including a malformed
  alpha key, an unknown ID, a valid beta key, and a mismatched secret, both candidate
  secrets are always compared with no early exit (except the existing missing-secret fast
  path). Duplicate secrets still yield the existing configuration error.
- Model deploy 1 starting at `T0`, the new key's `createdDate` at `T0 + 4 minutes`
  (second precision and a nonzero UTC offset, e.g. `2026-09-21T15:34:04+08:00`),
  and stack `UPDATE_COMPLETE` at `T0 + 9 minutes`. On simulated checker invocations
  at exactly `createdDate + 168 hours - 1 millisecond`, the threshold, and one
  millisecond after, expect respectively zero, one, and one overdue event for alpha.
  The first scheduled 09:00 UTC run at/after the threshold publishes one structured
  event to the rotation SNS topic, repeating once per later daily run while two keys
  exist. Neither stack completion nor a registry edit nor `lastUpdatedDate` moves this
  threshold. Both keys continue to authenticate through it. On recreating the
  secondary key, the new ID and `createdDate` start the new physical key's target;
  require an operator review and migration re-verification rather than silently
  treating the replacement as the same key.
- Give the checker `GetApiKeys` pages with `includeValues: false` and `GetApiKey` responses
  with `includeValue: false` and no `value` field; fail the test if it calls a
  value-returning API (including `GetUsagePlanKeys`) or puts a value in an alert/log.
  With one alpha key and no declared rotation, emit no overdue event; with two enabled
  alpha keys, emit the timed overdue event; with one enabled and one disabled alpha key
  in `old-disabled`, continue the same daily overdue events until deploy 3 leaves one.
  A registry declaration with only one key, two keys without a declaration, zero keys,
  or ambiguous/missing date metadata must surface an inconsistency, not a healthy result.
  Checker errors, including publish failures, trigger its Errors alarm; verify SNS
  subscription delivery before first rotation.
- Attribute keys by exact full names from the registry in a fixture with consumers
  `alpha` and `alpha-long`, including `alpha`'s `-b` key: each key counts only for its
  owner, regardless of prefix or enabled state. Reject a registry containing both
  `alpha` and `alpha-b` because their generated slot names collide. Duplicate deployed
  names must produce an ambiguity alert, not a guessed owner; no tags or key values
  are needed for the supported, collision-free naming scheme.
- With alpha's two keys still present after the seven-day target and beta healthy, plain
  `cdk deploy` is never blocked by stale rotation: test an unrelated stack fix, a shared
  Lambda asset change, a beta rotation, an alpha change preserving overdue overlap,
  a reviewed disable/rollback, and deploy 3 cleanup. No change-set/deploy guard is
  invoked or required, even if checker metadata is unavailable; the checker reports
  its own failures instead. Resuming, rolling back, or cleaning up after the alert
  requires Chip's human decision, not an automatic deadline action.
- Simulate a disabled-key 403 access record once with the `apiKeyId` field equal to the
  fixture ID `alpha-a` and once with that field equal to `"-"`: the runbook procedure
  must mark the field **verify at first use**, never count the `"-"` case as attributable
  old-key use, and require client-side correlation/rollback if a missed client is
  suspected. The pre-disable old-key zero-use gate applies in both cases.
- Baseline synthesis retains the current slot `a` logical ID. Overlap adds exactly one key
  and association. Disable changes only the old key's enabled state among key resources;
  both keys still exist. Cleanup retains slot `b` while deleting slot `a`; a reverse
  rotation then recreates slot `a` without replacing slot `b`. No SSM rotation
  parameters or post-deploy registrar are synthesized.
- Synthesized **ingestion** Lambda IAM policies are identical before and after the
  mechanism and every rotation phase; separately check the scheduled checker's minimal
  read/publish permissions and failure alarm.

Phase 5 must independently compare each proposed CloudFormation diff with deployed AWS
