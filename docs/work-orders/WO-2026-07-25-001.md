# Engineering Work Order — WO-2026-07-25-001

## Problem Statement
The new `schemaVersion: 2` device-status payload introduces two fields both
named `resetCount` at different paths:

- `firmware.resetCount` — the **live**, current value of the persisted
  reset counter.
- `startup.resetCount` — an **immutable snapshot** of that same counter,
  captured when the current execution finished initialization.

They are the same underlying counter observed at two different moments, not
two independent counters. The counter itself is narrow in scope (only
increments for pin/user/watchdog/optional user-application resets — not
sleep wakes, OTA, power-down, brownout, or panic) and is reset to zero by
daily cleanup, so it is neither monotonic nor a lifetime count.

Existing fleet-ops logic in `current-state.ts` (~line 223) and
`anomaly-detection.ts` (~line 114) may treat "a resetCount value" as a
health/anomaly signal without accounting for the live/snapshot distinction
or the daily-cleanup reset behavior.

## Operational Impact
Risk of false-positive anomaly flags in Fleet Ops once the six v21 soak
devices begin publishing `schemaVersion 2` payloads — specifically during
the window being used to judge whether the June 2026 PMIC/charging issue is
resolved. This is a data/decision-quality risk, not a device-safety risk:
worst case is a misleading dashboard, not device malfunction.

## Repository, Branch, Build, and Device Scope
- Repo: `particle-fleet-operations`
- Applies to any device publishing `schemaVersion 2` payloads — currently
  the six Boron soak devices once they receive firmware v21.

## Root Cause / Hypothesis
Confirmed by independent investigation: the two `resetCount` fields share
one underlying counter with different temporal semantics (current value vs.
value-at-last-startup). Any code path that reads either field as an
unqualified "reset count" risks manufacturing false increases (comparing
live-0 against snapshot-2), double-counting, or misreading the routine daily
reset-to-zero as improved health.

## Approved Architecture / Fix
Minimal guard, not a redesign:
1. In `anomaly-detection.ts`, suspend resetCount-based anomaly checks (or
   gate them behind an explicit, correctly-scoped comparison) until the
   Event History work (separate, upcoming Work Order) lands.
2. In `current-state.ts`, ensure both fields are surfaced under their full,
   distinct paths (`firmware.resetCount`, `startup.resetCount`) — never
   merged or flattened into a single `resetCount` value.
3. Do not derive a health/anomaly signal from either raw count in this
   Work Order.

## Acceptance Criteria
- A payload with `firmware.resetCount = 0` and `startup.resetCount > 0`
  (post-daily-cleanup case) does not trigger a false anomaly.
- Both resetCount fields remain visible and distinctly labeled in
  CurrentState output.
- No regression in existing `schemaVersion 1` anomaly detection.

## Required Tests
- Unit test: simulated post-daily-cleanup payload (live=0, snapshot>0) →
  no anomaly raised.
- Regression test: existing `schemaVersion 1` payloads → unaffected.
- Unit test: CurrentState output exposes both fields under distinct paths.

## Expected Post-Change Telemetry
No firmware change involved. Expect zero anomaly-flag entries attributable
solely to the live/snapshot resetCount discrepancy once the six soak
devices report on `schemaVersion 2`.

## Compatibility Requirements
Must remain backward compatible with `schemaVersion 1` payloads. No
firmware changes required or permitted under this Work Order.

## Security Considerations
None identified — logic-only change, no new external inputs, no
credential or access changes.

## Rollback Procedure
Revert the patch to `current-state.ts` / `anomaly-detection.ts`. No stored
data is affected (S3 raw archive is untouched regardless of this change),
so rollback carries no data-loss risk.
