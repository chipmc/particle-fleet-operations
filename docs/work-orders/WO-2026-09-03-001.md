# WO-2026-09-03-001 — `serial`/`watch` cursor silently drops rows on cross-format `eventTime`

**Status:** Ready to dispatch. Not yet started.
**Confirmed against:** merged `main` (`540d9cc`) — re-verified in this session, not carried forward from earlier investigation.
**Related but distinct from:** WO-2026-08-28-004 (closed, `540d9cc`) — that WO fixed the identical failure class on the `--start`/`--until` window path. This WO covers the one path it did not touch: the polling cursor used by `serial --follow` / `watch`.

## Read this first — this is Defect 2's exact signature, on a different code path

WO-004 fixed cross-format `eventTime` handling for bounded window queries. It explicitly did not fix the cursor comparison used by `--follow`/`watch`, because that comparison lives in different code (`compareEventToCursor`) and follows a different mechanism. This WO closes that remaining gap. Do not treat it as "the same fix, copy-pasted" — the mechanism is different enough that the naive fix (below) is actively wrong.

## The defect

Reproduction, confirmed against `540d9cc`:
```
cursor: ...500Z
row:    ...500500+00:00   (0.5ms after the cursor, chronologically)
--limit 1  →  returns ["cursor"], truncated: false, exit 0
```
The newer row is silently dropped. No flag, no error, exit 0.

## Root cause

The scan walks the sort key **descending as a string** (`--no-scan-index-forward`, `tools/telemetry:2329`). The stop test compares **parsed instants** (`compareEventToCursor`, `tools/telemetry:2431`).

Those two orderings invert across encodings: `.500Z` sorts lexicographically higher than `.500500+00:00`, but chronologically it is 0.5ms *earlier*. So the string-ordered scan returns the cursor row first; the instant-based stop test looks at it, concludes the scan has caught up to the cursor, and breaks (`tools/telemetry:2184`) — before ever requesting the row that is chronologically newer but lexicographically "behind" in the string scan.

**Restated as the rule any fix must satisfy:** "the oldest row in this page is at or before the cursor" does **not** imply "no row newer than the cursor remains unfetched." A correct fix has to account for the fact that the scan order and the completeness test are using two different, non-interchangeable notions of "order."

## Named trap — do not do this

**Do not make the cursor comparison lexicographic** (i.e., switch `compareEventToCursor` to string comparison to match the scan order). This looks like the obvious fix — align the two orderings — and it is wrong: it reintroduces the exact cross-format inversion that `comparePreciseInstants` (built during WO-004) exists to prevent. That would trade this defect for the original Defect 2, on a different path. If you find yourself reaching for this fix, stop and reconsider — the two orderings can't just be made to match, because the underlying data genuinely has two incompatible sort keys until WO-2026-08-28-003 Parts A/B lands.

## Fix direction

Not prescribed — this needs the same care WO-004's Step 0 didn't get on the first pass. At minimum, the fix must:
- Not assume the scan and the stop condition can share one ordering, given the underlying data is cross-format until canonicalization lands.
- Correctly handle the case where a chronologically-newer row sorts lexicographically "behind" the cursor in the string-ordered scan — likely means the stop condition needs to keep scanning past the string-order match point until it can positively rule out any remaining newer row, not stop at the first lexicographic match.
- Be validated with a fixture that specifically includes a cursor and a row straddling this exact inversion (as in the reproduction above), not just same-format cases.

## Cost consideration — measure, don't assume

`--follow`/`watch` polls repeatedly. Any extra scanning this fix requires is multiplied across every poll, which is a materially different cost profile from the one-shot window queries WO-004 dealt with. **Measure actual per-poll query/row cost of the fix**, don't just assert it's acceptable. This lands inside the same open query-cost question WO-004 left unresolved (noted there, not yet addressed) — don't let this WO quietly answer that question by default via whatever the first working fix happens to cost.

**Explicit constraint carried over from WO-004's Step 0 retirement:** any bound or cap introduced by this fix must not discard rows ahead of the filter the way Step 0's inner ceiling did. If a cost-bounding mechanism is needed, it must be checked against the same class of case that broke Step 0 — a bound that can be exhausted by scanning past in-window/in-scope rows before ever evaluating them.

## Process rules (carried forward from WO-004 — apply exactly, not as suggestions)

See also `docs/STYLE_GUIDE.md` §3 and §5, which now carry these rules repository-wide.

- **The reviewer (not the implementer) sets fixture parameters** — dataset size, number of rows near the cursor boundary, format mix. Three separate times in WO-004, implementer-chosen fixtures were too small to reach the defect they were meant to catch.
- **Any mock of DynamoDB must sort by string comparison, not parsed instant, and must be cross-checked against the live table before being trusted.** A mock that "correctly" sorts by parsed instant cannot reproduce this defect at all and would pass green against a broken fix. This is not hypothetical — a mock's `ExclusiveStartKey` semantics fabricated two entirely fictional regressions earlier in this project and cost two full review rounds before being traced to the mock itself.
- **Write the failing test first.** Run it against `540d9cc`, confirm it fails, and confirm it fails for the *correct* reason (the described row-drop, not e.g. a missing symbol or setup error) before writing the fix.
- **A widened or loosened assertion needs independent re-verification, not just internal consistency.** If a fix requires changing an existing test's expected value, that's a contract change — state it explicitly and confirm the new expectation against real/live data, not just against the new code's own output.

## Verification requirement before this is considered done

1. The reproduction case above (cursor `.500Z`, row `.500500+00:00`) returns both rows.
2. A fixture-based regression suite covering multiple cursor/row inversion cases across the format boundary, per the process rules above.
3. Per-poll cost measured (not asserted) for at least one realistic `--follow` scenario, and compared against pre-fix cost.
4. No regression against WO-004's existing 34-cell-equivalent matrix or the PR #18 truncation matrix — re-run both against the final code.
