# WO-2026-09-03-001 — `serial --follow` / `watch` drop cross-format rows adjacent to the cursor

**Status:** Drafted 2026-09-03. Not dispatched.
**Split from:** WO-2026-08-28-004, which closed Defect 2 on the `--start`/`--until` **window**
path and explicitly did not close it on the **cursor** path.
**Found by:** `codex exec` merge-gate round 2 on PR #20; reproduced and confirmed pre-existing.
**Touches:** `fetchWatchTimeline`'s backward paging loop — the loop protected by PR #18's
truncation matrix and by WO-2026-08-28-004's now-closed cells.
**Not a regression.** `main` before PR #20 (`c7e1bd0`) and after it (`540d9cc`) behave
identically here. Nothing to revert; this is an unclosed defect, not a break.

## The defect

`serial --follow` and `watch` advance a cursor and poll for events newer than it. An event
that is **chronologically after the cursor but lexicographically before it** is never
fetched. The poll reports success and emits nothing.

Confirmed against `540d9cc`:

```
cursor:  2026-07-14T08:00:40.500Z          (a pdiag/webhook row)
in table: 2026-07-14T08:00:40.500500+00:00  (a serialLog row, 0.5 ms LATER)

serial --limit 1  ->  events: ["cursor"]   truncated: false   1 query
```

The `.500500+00:00` row is inside the window, newer than the cursor, and never returned.
`truncated: false`, exit `0`, no warning. This is the same silent-omission class as
WO-2026-08-28-004's Defect 2 — *nothing was truncated; the row was simply never fetched.*

For a tool whose purpose is evidence, a tail that silently skips events is the worst
failure shape available, and it is worse than the window-path defect that WO-004 closed:
there is no flag, and a `--follow` session gives the operator no window boundary to
re-query and notice the gap.

## Root cause — the traversal and the stop test use different orders

**This is the load-bearing note. An implementer who "fixes the comparison" will not fix
this defect.**

- The scan is `--no-scan-index-forward` (`tools/telemetry:2329`): DynamoDB walks the
  stored sort key **descending as a string**.
- The stop test at `tools/telemetry:2184` is
  `compareEventToCursor(oldest, state.cursor) <= 0`, and `compareEventToCursor`
  (`tools/telemetry:2431`) compares **parsed instants** via `comparePreciseInstants`.

Across mixed encodings those two orders are inverted. Verified directly:

| | as a string | as an instant |
|---|---|---|
| `...40.500Z` vs `...40.500500+00:00` | `.500Z` sorts **higher** (`'Z' > '5'`) | `.500Z` is **earlier** by 0.5 ms |

So a descending-string page returns the cursor row **first**, the loop computes
`oldest` = the cursor row, concludes it has caught up, and breaks at `:2184` — before
applying `page.nextExclusiveStartKey` at `:2186`. The later row sits one page further into
the string order and is never requested.

Restated as the rule the fix must satisfy: **"the oldest row in this page is at or before
the cursor" does not imply "no row newer than the cursor remains unfetched"** while the
traversal order and the cursor order disagree.

### Two fixes that look right and are not

1. **Making the cursor comparison lexicographic.** This aligns the stop test with the
   traversal and appears to fix the case. It re-introduces Defect 2's original inversion,
   which is exactly why `comparePreciseInstants` exists. Both orders are individually
   correct; the defect is that they are *mixed*. Do not "fix" this by deleting the precise
   comparison.
2. **Widening further.** The bound is already widened to the whole second and both rows are
   inside the queried range. Widening is not the problem here — the range is right and the
   loop stops early inside it. A wider bound changes nothing.

## Fix direction

The loop must not treat a page's oldest row as proof of catch-up while encodings are mixed.
Some candidates, in rough order of preference — **the implementer must state which was
chosen and why, and must measure the cost (see below), not assume it:**

- **Exhaust the widened range, filter client-side.** Continue while
  `nextExclusiveStartKey` exists, and decide emission per row with
  `compareEventToCursor`. Correct by construction; the expensive option — see Cost.
- **Bound the over-scan.** Only rows sharing the cursor's whole-second prefix can invert
  against it, because the encodings differ only below the second. Continuing to page while
  the scan is still inside the cursor's second — and stopping once the scan has passed
  below it — is sufficient and bounded. This looks like the right shape; it needs proving,
  not assuming.
- **Canonical `eventTime`.** Once WO-2026-08-28-003 Parts A and B land, string order and
  instant order agree and the existing stop test becomes correct. That is the real fix, and
  it retires this WO rather than implementing it.

### Cost — must be measured, not asserted

`--follow` and `watch` poll on an interval. Any fix that scans further per poll multiplies
across every poll for the life of the session, which is a different cost profile from the
one-shot window path. WO-2026-08-28-004 deliberately left query work **unbounded** and
opened the question of whether large-window cost needs bounding against real fleet usage;
this WO lands inside that question. Report queries-per-poll before and after, at the
default poll interval, for both a quiet device and a chatty one.

Any bound introduced here must not repeat Step 0's mistake: **do not discard rows ahead of
the filter.** Step 0 was retired from WO-004 for exactly that, and one of its two bounds
was itself causing a 0-of-6 silent loss.

## The HTTP arm

`tools/telemetry:2172` is the same shape on the HTTP transport and is presumably affected
in the same way. It is **out of scope** here — HTTP is WO-2026-08-29-001 and is blocked on
canonicalisation — but the implementer must **state** the HTTP arm's before/after behaviour
rather than change it silently. A fix that alters HTTP as a side effect is a finding to
report, not an edit to make.

## Verification requirements

### Fixture parameters are set by the reviewer, not the implementer

Carried forward from WO-2026-08-29-001, where this had already failed three times. The
reviewer specifies, before implementation begins:

- the **encodings** on both sides of the cursor, including a pair that inverts (`.NNNZ`
  against `.NNNNNN+00:00` within one second) and a pair that does not;
- the cursor's own encoding — **both** must be exercised, since the inversion is
  directional and a cursor in the other encoding may hide it;
- the `--limit` values, including 1;
- the expected event **identities**, not just counts or the truncation flag.

An implementer may add cases but may not narrow, resize, or re-encode a specified one.

### Mocks must be cross-checked against the live table

A mock modelling `ExclusiveStartKey` as a positional offset rather than a key produced two
false blocking defect reports across two rounds of WO-2026-08-28-004. Any harness used as
evidence here must be validated against the real table first, and the mock's **sort order
must be a string comparison**, since that is what DynamoDB does and it is the entire
mechanism of this defect. A mock that sorts by parsed instant cannot reproduce it and will
pass green against the live defect.

### Gates

- The reproduction above returns **both** rows, oldest-first, `truncated: false`, exit `0`.
- The mirrored case with the encodings swapped.
- A multi-poll `--follow` sequence where the cursor advances across an inverting pair, with
  no event emitted twice and none skipped.
- WO-2026-08-27-001's truncation matrix: 0 failures.
- WO-2026-08-28-004's closed cells must not move — in particular the dense same-second
  windows (6/6 on both commands over Dynamo), the cross-format collisions (2/2), and
  `ceil(N/limit)` query counts at `--limit` 1/2/25.
- Every new test shown to **fail** against `540d9cc`, with output pasted.
- Queries-per-poll reported before and after (see Cost).
