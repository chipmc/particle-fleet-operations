# WO-2026-08-04-001: Add `--start` time range to `telemetry serial`

## Context

`telemetry serial <deviceId> --since <window>` currently only supports a
rolling lookback window (e.g. `--since 48h`) ending at "now" (or at
`--until`, if given). There was no way to anchor a bounded window to an
absolute historical start time without computing a duration by hand.

This became a real limitation during the Boron-Dev-09 SOC/charge-state
investigation: pulling a wide `--since` window to bracket a known historical
event (a SOC jump on 2026-07-31) surfaced far more recent, higher-volume
traffic than the operator wanted before reaching the window that actually
mattered.

## Investigation Findings (2026-08-04)

Investigated directly by reading source (`tools/telemetry`,
`tools/event-presentation.js`, `lambda/src/query/timeline.ts`,
`lambda/src/utils/query-params.ts`) and independently corroborated by
`codex exec`. Both converged on the same conclusions, which correct two
assumptions in the original draft and substantially narrow the scope:

1. **Endpoint confirmed, but plane filtering is client-side, not a query
   param.** `telemetry serial` does call `GET /device/{deviceId}/timeline`
   — via `startSerial` → `fetchSerialTimeline` → `fetchWatchTimeline` →
   `fetchTimelinePage` (`tools/telemetry:110`, `:1778`, `:1919`, `:1948`),
   which builds `start`/`end`/`limit` query params and requests
   `.../timeline?start=<ISO>&end=<ISO>&limit=<n>` (`tools/telemetry:1958-1963`).
   There is **no `plane=serial` parameter** — the API doesn't support one
   (`docs/API.md:46`). Every event in the window (all planes) is fetched,
   then classified client-side by `presentEvent()`
   (`tools/event-presentation.js:15-38`), and `buildSerialEntries`
   (`tools/telemetry:1782-1800`) keeps only `SERIAL` (and, with
   `--include-collector`, `COLLECTOR`) entries. **This means a bounded
   window still pays the "row budget" for non-serial traffic in that
   window**, not just serial rows — relevant context for why a wide
   `--since` felt like it was "burning through" a cap on unrelated traffic.
   (When no webhook secret is configured, this path falls back to a direct
   DynamoDB query instead — `tools/telemetry:764-821` — same start/end
   semantics, different transport.)

2. **`--until` and `--limit` already exist for `serial` today.** Contrary to
   the original draft's assumption, both flags are already implemented:
   - `--until <ISO timestamp>` is an existing absolute end-of-window flag,
     defaulting to now if omitted (`tools/telemetry:381-382`, help text at
     `:309`). It already fills the role the draft's proposed `--end` would
     have played.
   - `--limit <count>` is an existing flag (`tools/telemetry:375-376`),
     default **25** (`DEFAULT_TIMELINE_LIMIT`, `tools/telemetry:21`) — not
     100 or 1000. The CLI always sends an explicit `limit` to the API, so
     the API's own default (100) never applies here
     (`lambda/src/query/timeline.ts:39-44`).

3. **The "1000-row cap" was very likely `--limit 1000` used explicitly, not
   a hidden default.** The API rejects any `limit` over 1000 outright
   (`lambda/src/utils/query-params.ts:177-178` — throws, does not silently
   truncate). Given the CLI's real default is 25, someone investigating
   Boron-Dev-09 most plausibly passed `--limit 1000` by hand to try to pull
   more history in one shot. That value both (a) requests up to 1000 rows
   per API page, and (b) caps the number of *emitted* SERIAL rows
   client-side once `state.serialRowsEmitted >= options.limit`
   (`tools/telemetry:1792`). Because plane filtering happens after fetch,
   that emitted-row quota can be consumed by recent non-serial-adjacent
   noise before older SERIAL rows in the requested window are ever reached
   — which matches the reported symptom. There is no separate hard-coded
   1000-row ceiling in the pagination loop itself
   (`tools/telemetry:1919-1946`); it pages backward via a `while(true)` loop
   with no total-row stopping condition.

4. **`--since` is already fully client-side windowed with explicit
   start/end** — it does not pass `hours` to the API. `createWatchState()`
   computes `timelineStart = ISO(end - sinceMs)`, where `end` is `--until`
   or now (`tools/telemetry:1736`, `:1907-1908`), and those explicit ISO
   values are what's sent as `start`/`end` (`tools/telemetry:1919-1934`).
   **Adding `--start` is therefore not pure query-param plumbing** — it
   requires updating this same client-side window-calculation logic
   (`createSerialState`/`createWatchState`), not just adding a new flag that
   forwards a value to the API.

## Scope Change

Given the above, this WO narrows to:

- Add **`--start <ISO8601>`** as a new flag — an absolute alternative to
  `--since` for the window's start boundary.
- **Reuse the existing `--until`** as the end boundary; do **not** add a
  redundant `--end` flag. (Flagging this as a decision point: if you'd
  rather match `docs/API.md`'s `start`/`end` naming exactly for
  discoverability, we can add `--end` as a documented alias for `--until`
  instead — purely a naming call, not a behavior difference. Recommend
  keeping just `--until` since it already ships and works.)
- `--start` and `--since` are mutually exclusive (both set the start
  boundary) — new validation.
- `--start` without `--until` defaults the end to now — this already falls
  out of existing `--until` handling once `--start` feeds the same window
  calculation `--since` currently feeds.
- The "unbounded backward window" guard the original draft wanted for
  "`--end` only" is **already effectively in place**: `validateSerialOptions`
  today requires either `--since` or `--follow`
  (`tools/telemetry:1767-1769`); this just needs to also accept `--start`
  as satisfying that requirement.
- Truncation surfacing: still net-new, still needed. `buildSerialEntries`
  already knows, per-entry, when the emitted-row cap is hit
  (`tools/telemetry:1792`) — track whether that ever fired during a
  non-follow run and print an explicit warning (e.g. "results truncated at
  N rows (--limit), narrow your --start/--until range or raise --limit").
  Word this in terms of the *effective `--limit` in use* (default 25),
  not "the 1000-row cap" — 1000 is only the API's hard ceiling on the
  `--limit` value itself, not the CLI's operating default.
- No API or Lambda changes: `start`/`end` already exist and work at
  `GET /device/{deviceId}/timeline` exactly as documented. This is a
  CLI-only change.

## Acceptance Criteria

- `telemetry serial <deviceId> --start X` (no `--until`) returns SERIAL rows
  in `[X, now]`.
- `telemetry serial <deviceId> --start X --until Y` returns SERIAL rows in
  `[X, Y]`.
- `--start` and `--since` together error with a clear message.
- Providing neither `--start` nor `--since` (and not `--follow`) still
  errors, same as today's `--since`-required behavior.
- When the emitted-row cap (`--limit`, default 25) is hit within a
  `--start`/`--until` (or `--since`/`--until`) window, the CLI explicitly
  says so in its output rather than silently returning a partial result
  that looks complete.
- Existing `--since`-only and `--since`+`--until` usage is unaffected
  (regression check).

## Required Tests

- `--start` (no `--until`) returns the correct window, defaulting end to
  now.
- `--start` + `--until` returns only rows within `[start, until]`.
- `--start` + `--since` together errors.
- Neither `--start` nor `--since` given (and no `--follow`) errors.
- Truncation message appears when the emitted-row cap is hit within a
  bounded window; does not appear when it isn't.
- Existing `--since` and `--since`+`--until` regression tests still pass
  unchanged.

## Permitted Files

- `tools/telemetry` — flag parsing (`parseOptions`), `validateSerialOptions`,
  `createSerialState`/`createWatchState` (window calculation), and the
  truncation-warning output path.
- `tools/telemetry.test.js` — corresponding test coverage.

## Protected Areas

- `lambda/src/query/timeline.ts`, `lambda/src/utils/query-params.ts` — no

  investigation.
- `infra/` — no changes.

  logic is unaffected by this WO.
