# Engineering Work Order — WO-2026-07-26-002

## Problem Statement
Per the architecture now committed at `docs/architecture/data-model.md`,
CurrentState is an intentionally disposable projection — it holds only the
latest report per device. Several operationally meaningful signals are
already computed today but overwritten on every new report, exactly
reproducing the resetCount problem (WO-2026-07-25-001) for five other
signal types:

- Anomalies (`buildAnomalies()`/`detectAnomalies()`)
- Firmware version changes (`firmware_change`)
- Battery-critical transitions
- Device recovery (offline → online)
- Ledger sync failures (currently reach only `console.info`, never persisted)

None of this data is derived from scratch — it's already computed in the
ingestion path today and simply discarded on the next report.

## Operational Impact
Without event history, there is no way to answer "how many times did this
device go critical this week" or "how often is ledger sync failing" — only
"what is true right now." This blocks any future health scoring or trend
analysis, and it's the direct cause of the exact class of problem the
resetCount investigation surfaced.

## Repository, Branch, Build, and Device Scope
- Repo: `particle-fleet-operations`
- Fleet-wide; no device-specific scope

## Evidence
Claude Code investigation (research only): ingestion flow confirmed in
`lambda/src/handler.ts` → `ingestion.ts` (`handleIngestion()`), which
calls `storeRawEvent()` (S3), `indexEvent()` (existing `log-events` table,
`storage/dynamo.ts`), and `updateDeviceCurrentState()` +
`refreshDeviceStatusLedger()` (CurrentState, try/catch-isolated,
best-effort). CurrentState table schema confirmed at
`infra/infra-stack.ts:40-48` (partitionKey `projectId`, sortKey
`deviceId`, PAY_PER_REQUEST, point-in-time recovery on). IaC is AWS CDK,
single stack (`infra/lib/infra-stack.ts`, entry `infra/bin/infra.ts`).
Per-event-type derivability confirmed by direct grep — the five types
below have zero new extraction required; the remaining seven proposed
types (BOOT, WATCHDOG_RESET, LOW_POWER_POLICY_ENTERED/EXITED,
CONNECT_TIMEOUT, DEVICE_OFFLINE, OTA_START/OTA_COMPLETE) each need new
extraction, a scheduled component that doesn't exist, or data from
outside this repo — all explicitly deferred (see Non-Goals).

**Design note, corrected after investigation:** EventHistory is
append-only — each event is a new item, never an update to an existing
one. It should use `PutCommand` (full-item writes) exclusively, matching
the existing `log-events` table's already-safe pattern
(`storage/dynamo.ts`). This write shape is structurally immune to the
`ExpressionAttributeNames`/`UpdateExpression` bug class found in
WO-2026-07-25-001's round 2, since it never uses `UpdateExpression`. The
missing shared update-expression utility (confirmed absent; three
separate hand-rolled patterns exist in `current-state.ts`) remains a real
risk, but it's a risk for *update* paths specifically — it does not block
or apply to this Work Order, since EventHistory doesn't do updates.
Retrofitting `current-state.ts`'s two remaining hand-rolled `UpdateCommand`
paths into a shared utility is valuable but is separate, deferred cleanup
(see Non-Goals) — not a prerequisite here.

## Approved Architecture / Fix
1. New DynamoDB table, declared in `infra/lib/infra-stack.ts` alongside
   the existing two: partition key `deviceId`, sort key `eventTime`
   (matching `log-events`' access pattern, since this is a log, not a
   projection). `grantWriteData` to `ingestionFunction`, a `CfnOutput`,
   and a new env var (e.g. `EVENT_HISTORY_TABLE_NAME`) passed to the
   Lambda, matching the existing `DEVICE_CURRENT_STATE_TABLE_NAME`
   pattern.
2. In `ingestion.ts`, add a third branch in `handleIngestion()`, sibling
   to the existing CurrentState update step: same try/catch isolation,
   same best-effort/non-blocking behavior (`console.warn` on failure,
   ingestion still succeeds) — EventHistory availability must never
   affect ingestion reliability.
3. Generate exactly these five event types on their existing trigger
   conditions, each as a `PutCommand` full-item write:
   - `ANOMALY` — from existing `buildAnomalies()`/`detectAnomalies()` output
   - `FIRMWARE_UPDATE` — from existing `firmware_change` detection
   - `BATTERY_CRITICAL` — from existing battery threshold logic
   - `DEVICE_RECOVERED` — from existing offline-candidate comparison
   - `LEDGER_SYNC_FAILED` — from `ledger-refresh.ts`'s existing failure
     signal (`result: 'failed'`, `errorKind`, `httpStatus`), currently
     logged but never persisted

## Explicit Non-Goals
- `BOOT`, `WATCHDOG_RESET`, `LOW_POWER_POLICY_ENTERED/EXITED`,
  `CONNECT_TIMEOUT` — need new field extraction; future WO
- `DEVICE_OFFLINE` — needs a scheduled/polling component that doesn't
  exist in this architecture; future WO
- `OTA_START`/`OTA_COMPLETE` — need data from outside this repo; future WO
- Retrofitting `current-state.ts`'s remaining hand-rolled `UpdateCommand`
  paths into a shared utility — separate cleanup item
- Any new CLI/report read surface for EventHistory (e.g. `telemetry
  events`) — separate follow-up WO once write-path value is proven;
  verification for this WO is via direct DynamoDB query
- Any health-scoring logic — this WO only persists events, scores nothing
- Decommissioning or modifying `log-events` — separate, tied to firmware
  rollout completion timeline, not part of this WO

## Acceptance Criteria
- All five event types are persisted to EventHistory via `PutCommand` on
  their respective existing trigger conditions.
- EventHistory write failures are non-blocking — ingestion succeeds even
  if the EventHistory write fails.
- Table follows `deviceId`/`eventTime` partition/sort key convention.
- No change to S3 storage, `log-events` indexing, CurrentState
  projection, anomaly detection, or `tools/telemetry` report behavior.
- Verifiable via direct DynamoDB query (no new CLI tooling required).

## Required Tests
- Unit test per event type (5 total): trigger condition met → correct
  EventHistory item written with correct `deviceId`/`eventTime`/type/payload.
- Unit test: EventHistory write failure (mocked) → ingestion still
  succeeds (non-blocking behavior preserved).
- Regression test: existing CurrentState/S3/anomaly-detection/report
  behavior unchanged.

## Expected Post-Change Telemetry
No firmware changes. Expect EventHistory items to begin appearing for the
six soak devices as anomalies, firmware changes, or ledger sync issues
naturally occur — no immediate visible change to any existing report
output, since read-side tooling is explicitly out of scope.

## Compatibility Requirements
No changes to any existing table schema, API, or CLI output.

## Security Considerations
New table follows existing IAM grant pattern (`grantWriteData`, scoped to
the ingestion Lambda only). No new external inputs.

## Rollback Procedure
Revert the patch. New table can be left in place empty (low cost, per-
request billing) or removed via CDK if desired — no dependent readers
exist yet since this WO adds no read path.
