## Goal

Let a consumer rotate its API key without an outage, with overlap, which neither keys nor secrets have today. Keep the redesign no bigger than it needs to be.

## Current behavior (evidence)

**One key ID per consumer.**
- `infra/lib/infra-stack.ts:733-754` creates one `ApiKey` per registry consumer and adds it to that consumer's usage plan (`:746`). It then passes the key's ID to the Lambda as one environment variable, `INGESTION_API_KEY_ID_<CONSUMER_ID>` (`:753-754`).
- `lambda/src/consumer-auth.ts:140-151` (`buildApiKeyConsumerLookup`) reads exactly that one variable per consumer (`:146`) into a key-ID-to-consumer map.
- The lookup is built on every request at `lambda/src/ingestion.ts:57`.

**A second key fails in the Lambda.** A second key on the same usage plan would pass API Gateway's check. The Lambda would then find no consumer for its ID and reject the request as `credential_pair_mismatch` (`consumer-auth.ts:125`), a 401.

**No secret overlap.** `loadConsumerSecrets` (`consumer-auth.ts:47-59`) calls `GetSecretValue` with only `SecretId` (`:52`), which returns the secret's current version. Nothing reads a pending or previous version. Today a webhook-secret rotation rejects clients still sending the old value from the moment the new value is live until each client is updated. The Lambda caches secrets for up to 5 minutes (`CACHE_TTL_MS`, `:29`), so the switch is not instant.

**Why overlap matters most for one consumer.** `particle-cloud-webhook` has one key and one secret shared by six Particle Cloud webhooks. Each webhook's headers are edited separately in the Particle Console, so the six clients can only be updated one at a time.

**Rotation is currently blocked.** The API key rotation procedure in `docs/security/webhook-secret-rotation-runbook.md` (PR #41) is marked blocked on this work order. So is the deferred rotation of key ID `mqdbypomt7` recorded on 2026-09-28 (PR #40).

## Questions the design must answer

1. **Scope: keys only, or keys and secrets together?** Say plainly whether fixing the API key side alone is worth doing on its own, or whether both should be designed together because they are the same underlying problem. Give the reasoning either way. If they are split, say how the key design avoids constraining the later secret design.
2. **Declaring a second credential.** How a second key (and, if in scope, a second secret version) for one consumer is declared: in the registry (`config/ingestion-consumers.json`), in CDK, or both. The registry is the documented single source of truth for consumers (`infra-stack.ts:714-715` comment). API key IDs exist only after CDK creates the resource, which is why they are passed to the Lambda through environment variables today.
3. **Bounding the window.** How the rotation window is bounded, and what stops an overlap from becoming permanent by being forgotten.
4. **Resolving back to one credential.** How rotation completes cleanly: the old key is disabled, then deleted, and its ID removed from the Lambda's mapping. State which deploys this takes and what each `cdk diff` should show.
5. **Telling the two keys apart in logs.** How `ingestion_auth` log entries and access-log `apiKeyId` values tell the old and new keys apart during the window. The runbook's step 5 depends on this to prove the old key is unused.

## Constraints the design must preserve

- **Pair check.** A request is accepted only when its API key and its webhook secret resolve to the same consumer (`consumer-auth.ts:122-126`). Overlap must not let one consumer's key pair with another consumer's secret.
- **Constant-time comparison.** Every candidate secret is hashed and compared with `timingSafeEqual`, with no early exit (`consumer-auth.ts:74-79`, `:99-108`). If secret overlap is in scope, the extra candidate versions must keep this property.
- **Duplicate-secret detection.** Two different consumers holding the same secret value is refused as a configuration error (`consumer-auth.ts:113-119`). One consumer holding two versions during a rotation must stay distinguishable from that error.
- **No secret values in environment variables.** Per-consumer secrets are read by name at runtime. The design must not move a secret value into the Lambda environment. Key IDs are not sensitive and may stay there.
- **No rotation by resource rename.** Renaming the existing `ApiKey` logical ID makes CloudFormation create the new key and delete the old one in the same deploy, which is exactly the outage this work order exists to prevent. The design must not depend on it.
- **Credentials printed in output.** Any command the design or its runbook prescribes must identify keys by ID only (`docs/STYLE_GUIDE.md` §8, PR #41).
