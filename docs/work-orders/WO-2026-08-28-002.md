# WO-2026-08-28-002: `watchEventId` does not implement the documented row identity

## Context

Deferred from WO-2026-08-27-001 (round-5 review, PR #18). Surfaced when a fix
prescribed during that work order keyed deduplication on `watchEventId` and
silently dropped a row; the in-batch case was fixed there, and the underlying
identity mismatch was scoped out to this work order.

**Read the severity assessment below before scheduling this.** The defect is
real and demonstrable, but is not reachable through the current ingest path. It
is a latent contract violation, not an active data-loss bug.

## Investigation Findings (2026-08-28)

Verified against `main` at `0f70dbd`.

### 1. The code does not match the documented contract

`docs/tools.md:330` states: *"The command preserves distinct rows by `eventTime +
eventId`, with `s3Key` as the event identity fallback."*

`watchEventId` (`tools/telemetry:2193`) implements something different:

```js
return stringValue(event.eventId) || stringValue(event.s3Key) || `${event.eventTime}:${event.eventName}`;
```

`eventTime` is used only in the last-resort fallback. Two distinct rows sharing
an `eventId` — or sharing an `s3Key`, when `eventId` is absent — are treated as
the same row.

### 2. Demonstrable data loss in `watch` and `serial --follow`

`collectNewTimelineEvents` (`tools/telemetry:2170`) filters against
`state.seenEventIds` using that identity, so a colliding row arriving in a later
poll is dropped and never advances the cursor. Reproduced by driving
`runWatchLoop` directly with two distinct rows (different `eventTime`) across two
polls:

```
distinct rows sharing eventId across polls -> emitted ["1"],      expected ["1","2"]
distinct rows sharing s3Key  across polls -> emitted ["1"],      expected ["1","2"]
control, distinct eventIds                -> emitted ["1","2"]   correct
```

The same holds for `serial --follow`. It does **not** affect non-`--follow`
`serial` runs: `runSerialLoop` calls `buildSerialEntries` exactly once before
returning (`tools/telemetry:1841-1861`) and `fetchWatchTimeline` accumulates all
pages into a single array, so there is only ever one batch, and the in-batch
dedup added by WO-2026-08-27-001 already uses the correct `eventTime + identity`
composite (`tools/telemetry:1892-1897`).

### 3. Severity: latent, not active — the collision is unreachable today

Tracing how identities are produced:

- `eventTime` **is** `publishedAt` (`lambda/src/ingestion.ts:109`).
- `s3Key` = `particle-events/{date}/{eventName}/{deviceId}/{publishedAt}.json`
  (`lambda/src/utils/parse.ts:103-111`) — so `eventTime` determines `s3Key`.
- `eventId` = `sha256(deviceId ∥ eventName ∥ eventTime ∥ s3Key)`
  (`lambda/src/utils/parse.ts:209-218`) — so `eventTime` is inside the hash.
- The `ParticleLogEventsTable` key is `(deviceId, eventTime)`
  (`infra/lib/infra-stack.ts:30-32`), so one device cannot hold two rows with
  the same `eventTime`.

Therefore two distinct rows for a device always differ in `eventTime`, and so
always differ in `s3Key` and `eventId`. **The collision cannot occur through the
current ingest path.** It becomes reachable only if `eventId` is ever sourced
from somewhere other than that hash — for example Particle's own event id — or
if a second writer populates the table.

This is why the work order is scoped as a contract fix rather than a bug fix,
and why it is reasonable to defer or decline it.

## Scope

Pick one and apply it consistently:

**Option A — make the code match the documentation (recommended).** Give the
dedup sites the documented `eventTime + eventId` identity, keeping `s3Key` and
then `eventName` as fallbacks. The natural shape is a helper alongside
`watchEventId` returning the composite, used by `collectNewTimelineEvents` and
`markWatchEventSeen`; `buildSerialEntries` already composes it inline and should
be switched to the shared helper so there is one definition. Small, defensive,
and removes a documented-behavior mismatch.

**Option B — make the documentation match the code.** Amend `docs/tools.md:330`
to state that rows are identified by `eventId`, falling back to `s3Key` then
`eventTime + eventName`, and note that distinct rows sharing an identifier are
collapsed. Cheaper, but leaves a real trap for anyone who later changes how
`eventId` is produced.

Recommendation: **Option A.** The cost is one helper and its call sites, and the
documented contract is the one a future change would reasonably rely on.

## Acceptance Criteria

For Option A:

- Two distinct rows sharing an `eventId` but differing in `eventTime` are both
  emitted, in `watch` and in `serial --follow`, across polls as well as within a
  batch.
- The same holds for two rows sharing an `s3Key` with no `eventId`.
- Genuinely identical rows — the same row re-fetched at a page boundary — are
  still deduped to one, in both commands.
- The `--follow` cursor advances past a colliding row rather than stalling.
- One identity helper, used by every dedup site; `buildSerialEntries` no longer
  composes its own.
- No regression to WO-2026-08-27-001's truncation matrix (see that work order's
  Acceptance Criteria; exact-limit, grep-recovery and cap cases all still hold).
- `docs/tools.md:330` accurate for the resulting behavior.

## Required Tests

1. `watch`: distinct rows sharing an `eventId`, arriving in different polls →
   both emitted, cursor advances. Fails today.
2. `serial --follow`: same. Fails today.
3. Distinct rows sharing an `s3Key` with no `eventId` → both emitted. Fails today.
4. Identical row re-fetched at a page boundary → emitted once. Passes today;
   guards against over-correcting.
5. The in-batch cases already covered by WO-2026-08-27-001 continue to pass.
6. WO-2026-08-27-001's truncation matrix as regression.

Sequencing note recorded at dispatch: the Related Observation below states this
contract should be settled in light of WO-2026-08-28-003 Part A, because
canonicalising `eventTime` changes how `eventId` is generated and `eventId` is a
hash over `eventTime`. Dispatching ahead of Part A was Chip's explicit decision.
If Part A later changes the encoding, the composite identity implemented here
should still hold — it keys on `eventTime` as stored, whatever that encoding is —
but the fallbacks and the test fixtures will need rechecking against the new
form.

## Related Observation — superseded

This work order originally recorded a hypothesis that two events sharing a
`publishedAt` would overwrite each other in S3 and DynamoDB, since neither write
uses a condition expression.

**Investigated 2026-08-28 against live production data; not substantiated.** The
smallest inter-event gap observed was 0.813 ms, and `serialLog` — the
highest-rate producer — carries microsecond precision, so identical timestamps
are very unlikely. The overwrite path is still unguarded and remains
theoretically possible, but there is no evidence of it occurring and it is low
priority.

That investigation found something else, which is live in production and more
serious than anything in this work order: `eventTime` holds two incompatible
timestamp formats, so lexicographic order does not match chronological order and
bounded queries silently omit in-window events. See **WO-2026-08-28-003**, which
supersedes this observation.

Note that WO-2026-08-28-003 may also affect the priority of this work order: if
`eventTime` normalization changes how `eventId` is generated, the identity
contract described above should be settled in light of that, not before it.
