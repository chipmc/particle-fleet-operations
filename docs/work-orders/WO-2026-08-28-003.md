# WO-2026-08-28-003: Mixed `eventTime` timestamp formats silently drop events from bounded queries

## Context

Surfaced while investigating the ingest-overwrite hypothesis recorded as an
observation in WO-2026-08-28-002. **That hypothesis was not confirmed.** This was
found instead, and it is materially more serious: it is live in production data
today, it silently omits events from bounded queries, and the truncation
machinery delivered by WO-2026-08-27-001 cannot detect it — because nothing is
truncated. The query simply fails to match.

## Investigation Findings (2026-08-28)

Verified against **live production data** in `InfraStack` (account 564771499971,
`us-east-1`), table `InfraStack-ParticleLogEventsTableF654D709-OMOORL9AXLQM`.
All evidence below is real rows, not fixtures.

### 1. Two incompatible timestamp formats share one string sort key

`eventTime` is the DynamoDB sort key (`infra/lib/infra-stack.ts:30-32`) and is
set to `publishedAt` verbatim (`lambda/src/ingestion.ts:109`).
`extractTimestamp` (`lambda/src/utils/parse.ts:41-43`) does no normalization:

```ts
return body.published_at || body.timestamp || new Date().toISOString();
```

So each producer's own formatting is written straight into the sort key. Live
sample, 2,230 rows across 4 devices over 48 hours:

| device | rows | `.NNNNNN+00:00` | `.NNNZ` |
|---|---|---|---|
| e00fce688e592afaf23ac4fb | 655 | 491 | 164 |
| e00fce68399ee6244a963935 | 746 | 574 | 172 |
| e00fce683f6063bf254283dd | 802 | 13 | 789 |
| e00fce686548d46c4b45e380 | 27 | 0 | 27 |

The split is by producer: `serialLog` events carry microsecond precision with a
`+00:00` offset; `pdiag` and webhook events carry millisecond precision with `Z`.
Both are valid ISO 8601. **Neither sorts lexicographically in chronological
order against the other.**

### 2. Confirmed ordering inversion in production

```
2026-08-27T13:09:40.397Z         pdiag      <- earlier in time
2026-08-27T13:09:40.397813+00:00 serialLog  <- 0.813 ms later
```

String comparison puts them in the opposite order, because `'8' < 'Z'`. DynamoDB
stores and returns them reversed. One such inversion exists in a 48-hour,
4-device sample.

### 3. Live consequence: a bounded query silently omits an in-window event

Querying the real table with `--start` at the millisecond boundary, where the
`serialLog` row is 0.813 ms *inside* the window:

```
start = 2026-08-27T13:09:40.397Z
  2026-08-27T13:09:40.397Z          pdiag
  2026-08-27T13:09:41.311760+00:00  serialLog        <- .397813 MISSING
  ...

start = 2026-08-27T13:09:40.396Z   (1 ms earlier)
  2026-08-27T13:09:40.397813+00:00  serialLog        <- now present
  2026-08-27T13:09:40.397Z          pdiag
  ...
```

The event is in the requested window and is not returned. **No truncation flag,
no warning, exit 0.** This is the same failure class WO-2026-08-27-001 was
written to eliminate — a partial result presented as complete — reached by a
mechanism that work order's machinery cannot see, since the row was never
truncated, merely unmatched.

### 4. The same mechanism can drop rows during paging

`fetchWatchTimeline` sets `pageEnd` to the oldest row's `eventTime`
(`tools/telemetry:2058`) and the next page queries `BETWEEN :start AND :pageEnd`.
When that boundary is a microsecond value such as `...40.397813+00:00`, a
millisecond row at `...40.397Z` compares as *greater* and falls outside the
page, despite being chronologically earlier. The row is skipped and never
refetched. This is a fetch-level loss, invisible to the caller.

### 5. Client-side ordering is affected too

`tools/telemetry` compares and sorts `eventTime` as strings throughout —
`compareWatchEvents`, `compareEventToCursor`, and the serial entry sort. Mixed
formats therefore also mis-order displayed output and can mis-advance the
`--follow` cursor.

### 6. What was NOT confirmed

WO-2026-08-28-002's observation proposed that two events sharing a `publishedAt`
would overwrite each other in S3 and DynamoDB. That remains theoretically true —
neither write uses a condition expression — but no evidence of it was found. The
smallest inter-event gap in the sample was 0.813 ms, and `serialLog`, the
highest-rate producer, carries microsecond precision, making identical
timestamps very unlikely. **Treat the overwrite risk as unconfirmed and low
priority; this work order supersedes that observation.**

## Scope

The fix has a forward half and a backfill half, and they can ship separately.

### Part A — normalize at ingest (forward-looking)

Normalize `publishedAt` to one canonical representation before it is used as
`eventTime` or in `s3Key`. `new Date(value).toISOString()` yields
`YYYY-MM-DDTHH:MM:SS.sssZ` and sorts correctly, but **truncates microseconds**,
which raises collision risk for `serialLog` and must be weighed against
retaining sub-millisecond resolution in a fixed-width, `Z`-suffixed form.

Whichever is chosen, the canonical format must be fixed-width so lexicographic
order equals chronological order, and the choice must be documented in
`docs/contracts/`.

**This changes `eventId`**, which hashes `eventTime` and `s3Key`
(`lambda/src/utils/parse.ts:209-218`), and changes `s3Key` itself. Both
consequences need to be deliberate, not incidental.

### Part B — backfill existing rows

Existing rows keep their original format, so the defect persists for historical
windows until they are rewritten. A migration must rewrite `eventTime` (the sort
key, so this is delete-and-reinsert, not update), and consequently `eventId` and
`s3Key` references. This is the expensive half and needs its own plan — including
whether historical `serialLog` microsecond precision is preserved or truncated.

### Part C — defensive CLI handling — MOVED to WO-2026-08-28-004

> **Moved 2026-08-28.** Part C now lives in WO-2026-08-28-004, merged with the
> paging boundary fix, because both change the same code in `fetchWatchTimeline`.
> The description below is retained for context only. Note that WO-004 records a
> correction to it: client-side normalization alone cannot fix the server-side
> `BETWEEN` omission, because the comparison happens inside DynamoDB against the
> stored string key. The workable approach is to widen the query to whole-second
> boundaries and filter client-side on parsed instants.

Independent of A and B, `tools/telemetry` should not assume lexicographic order
equals chronological order. At minimum, parse `eventTime` for comparison and
sorting rather than comparing strings. This does not fix the server-side
`BETWEEN` omission — only A and B can — but it removes the client-side
mis-ordering and cursor hazards, and it protects against any future format drift.

Note that Part C alone would give correct *ordering* over incorrect *data*, which
may be worse than the current state for evidence purposes: the output would look
trustworthy while still missing rows. If Part C ships alone, that limitation must
be documented.

## Recommended sequencing

1. **Part A** — stops the problem growing. Small, contained to `lambda/`.
2. **WO-2026-08-28-004** (formerly Part C, now merged with the paging fix) —
   removes the client-side hazards and defends against pre-backfill rows.
3. **Part B** — the migration, planned separately once A has settled.

## Acceptance Criteria

- Every newly ingested event's `eventTime` is in the single canonical format,
  verified against real ingested data after deploy, not only unit tests.
- For any two events from one device, lexicographic order of `eventTime` equals
  chronological order — asserted over a real sample.
- A bounded query whose `--start` or `--until` falls inside a millisecond
  containing a sub-millisecond event returns that event. The reproduction in
  finding 3 must return the `serialLog` row.
- `eventId` and `s3Key` changes are deliberate and documented; any consumer of
  either is identified before Part A ships.
- No regression to WO-2026-08-27-001's truncation semantics.
- The canonical format is documented in `docs/contracts/`.

## Required Tests

1. `extractTimestamp` normalizes each observed producer format —
   `.NNNNNN+00:00`, `.NNNZ`, and no-fractional — to the canonical form.
2. Property test: for a set of timestamps in mixed input formats, sorting the
   normalized values lexicographically equals sorting the parsed instants.
3. Ingest end-to-end: a webhook with a `+00:00` microsecond `published_at`
   produces a canonical `eventTime`.
4. Regression against the exact production pair from finding 2
   (`.397Z` / `.397813+00:00`): after normalization they order correctly.
5. Part C tests: see WO-2026-08-28-004.
6. WO-2026-08-27-001's truncation matrix, unchanged.

## Permitted Files

- Part A: `lambda/src/utils/parse.ts`, `lambda/src/ingestion.ts`, their tests,
  `docs/contracts/`.

## Protected Areas

- Truncation reporting semantics from WO-2026-08-27-001.
- The DynamoDB key schema itself (`deviceId` / `eventTime`) — this work order
  changes the *values* written to the sort key, not the schema.
- Do not begin Part B before Part A is settled; rewriting rows into a format
  that later changes again would be the worst outcome.
