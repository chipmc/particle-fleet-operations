# WO-2026-08-05-001: Add regression tests for `timeline`/`serial` `--start`/`--until` wiring

## Context (as drafted)

Live testing after WO-2026-08-04-002 (PR #14) reported `timeline --start
<ISO8601> --until <ISO8601>` silently falling back to the default last-24h
window, plus a claim that `telemetry --help` still didn't show `--start` on
the `timeline` usage line.

## Investigation Findings (2026-08-05)

Investigated directly (manual tracing with mocked `fetch`/`awsJson` against
current `main` at `d35eba8`) and independently corroborated by `codex exec`,
including a `git show` diff of both commits in PR #14. **Both the described
bug and the help-text claim are already resolved on current `main` — neither
requires a code fix.**

1. **The bug is real, but already fixed.** PR #14 had two commits:
   `6e0f95e` (initial implementation) and `483b87e` (a follow-up I requested
   after review, merged as the final state of PR #14/WO-2026-08-04-002). At
   `6e0f95e`, `queryTimelineFromDynamo()` — the fallback path used when no
   webhook secret is configured — still read `options.start`/`options.end`
   directly instead of going through `resolveTimelineWindow()`, so CLI-parsed
   `startIso`/`until` were silently dropped there and it fell back to the
   default lookback window. That's precisely the symptom this WO describes.
   `483b87e` fixed exactly this (confirmed via `git show 483b87e -- tools/
   telemetry`, `tools/telemetry:784-788`), and current `main`'s
   `tools/telemetry` is byte-identical to `483b87e`. I independently
   confirmed on current `main`, with mocked `fetch` and mocked `awsJson`,
   that both the HTTP path (`fetchTimeline`) and the DynamoDB fallback path
   (`queryTimelineFromDynamo`) correctly resolve `--start 2026-08-01T08:00:00Z
   --until 2026-08-01T10:00:00Z` to that exact window — no `hours=` param
   leaks through, and the DynamoDB query's `:start`/`:end` expression values
   match exactly. **Conclusion: whoever did the "live testing" behind this
   WO almost certainly tested against a stale checkout — either before
   pulling PR #14's final merge, or against the intermediate commit
   `6e0f95e` before the follow-up fix landed. There is nothing to fix here.**

2. **The help-text claim is false on current `main`.** `tools/telemetry:143`
   (top-level `printUsage()`) and `:253`/`:271-273` (`timeline`-specific
   `printCommandHelp()`) already show `--start <ISO8601> [--until
   <ISO8601>]` on the `timeline` usage line — this was part of PR #14's
   first commit and was never missing on `main`. Both investigations ran
   `telemetry --help` and `telemetry timeline --help` directly and confirmed
   this. **Nothing to fix here either.** (Minor, unrelated, optional
   nitpick Codex noticed: the shared top-level Options list at
   `tools/telemetry:171` still describes `--start`/`--until` as "serial
   reconstruction" options even though `timeline` uses them too — cosmetic
   wording only, not blocking, not required.)

3. **The test-coverage gap is real and still worth closing — but a literal
   full-subprocess "end-to-end" test isn't the right shape.** Confirmed:
   nothing in `tools/telemetry.test.js` exercises `queryTimelineFromDynamo`
   with `--start`/`--until` and asserts on the resulting `:start`/`:end`
   values — this is exactly the gap that let the original bug ship
   undetected (the existing Dynamo-path tests build options manually and
   check pagination/event output, never the resolved time bounds). The
   existing HTTP-path test (`tools/telemetry.test.js:524`) already tests at
   the right level — `parseOptions()` output fed into `fetchTimeline()`
   directly with a mocked `fetch`, asserting on the constructed URL — but
   there's no equivalent for the Dynamo path. A literal `runTelemetry()`
   subprocess-spawn test (genuinely spawns the CLI script,
   `tools/telemetry.test.js:66`) *could* catch this class of bug, but only
   if it's also given a fake `aws` binary on `PATH` and stubbed device-
   inventory/CloudFormation calls so the spawned process can reach the real
   code path without live AWS access — that's meaningfully more test
   infrastructure than this WO's scope warrants for what's actually a
   contract-boundary bug (a downstream function reading stale property
   names that don't match what the parser actually produces). The
   proportionate fix: extend the existing pattern — call the real
   `queryTimelineFromDynamo()`/`fetchTimeline()` functions directly with
   parsed options and mocked `awsJson`/`fetch` — to cover the Dynamo path
   for both `timeline` and `serial`, asserting on the resolved `:start`/
   `:end` (or URL `start`/`end`) values. This would have failed at `6e0f95e`
   and passed at `483b87e` — proof it actually catches this class of bug.

## Scope Change

Given the above, this WO becomes test-only, much narrower than drafted:

1. No code fix to `timeline`'s wiring — already correct on `main`.
2. No `--help` text fix — already correct on `main`.
3. Add regression tests (not a full subprocess/AWS-stubbing end-to-end
   harness) that call `queryTimelineFromDynamo()` directly with parsed
   `--start`/`--until` options and a mocked `awsJson`, asserting the exact
   `:start`/`:end` values sent to DynamoDB — for both `timeline`'s direct
   call and `serial`'s call via `fetchTimelinePage()`. This closes the
   actual coverage gap that let the original (now-fixed) bug ship.
