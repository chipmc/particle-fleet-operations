# WO-2026-08-27-001: `telemetry` must not report success on a truncated result

## Context (as drafted)

`telemetry serial`/`timeline` truncate results against a default `--limit`
without signalling that truncation in a way a programmatic consumer can
detect. The truncation warning goes to stderr only; `--json` output includes a
count but no truncation flag; exit code is 0 either way. A consumer capturing
stdout and checking exit code sees a truncated result as complete success.

This already produced a near-miss: a search for specific log lines returned
zero hits from a truncated window and read as "confirmed absent" until a
separate line-count check caught that only a fraction of available lines had
actually been searched.

## Investigation Findings (2026-08-27)

Verified by running the real CLI end-to-end, not by reading source: a fake
`aws` executable on `PATH` (serving `cloudformation describe-stacks`,
`dynamodb scan` for device inventory, and a paginating `dynamodb query` over a
synthetic event set), a stub Particle product-inventory HTTP endpoint, and
`HOME` pointed at an empty temp dir so no `PARTICLE_WEBHOOK_SECRET` is present
and the DynamoDB fallback path is exercised. Every claim below is an observed
exit code / stdout / stderr from an actual `tools/telemetry` process, with the
underlying `dynamodb query` calls traced.

Two methodology corrections were applied mid-investigation and are recorded
here because they changed conclusions:

- The first fixture generated event timestamps from each `aws` subprocess's
  own `Date.now()`, so the dataset shifted by ~90ms per call and paging
  behavior was an artifact. The fixture was pinned to a fixed base instant and
  every paging-dependent result below was re-run against it.
- The first fixture also emitted multiple events per device sharing one
  `eventTime`. The DynamoDB key is `(deviceId, eventTime)`
  (`infra/lib/infra-stack.ts:30-32`), so that is impossible in production. All
  results below use distinct timestamps.

Independently corroborated by `codex exec` (read-only, same tree). Codex
returned CONFIRMED on the predicate ordering, the boundary false positive, the
paging termination defect, and the exit-code inventory; PARTIAL on the
`timeline` envelope shape, with a qualification that is folded into finding 3
below. Codex also supplied the key-schema correction above.

### 1. The drafted premise is confirmed

| Command | dataset vs `--limit` | exit | stderr | stdout |
|---|---|---|---|---|
| `timeline --json --limit 5` | 40 events | **0** | `WARN: results truncated at 5 events (--limit)…` | envelope with `count: 5`, no truncation field |
| `serial --json --limit 5` | 40 events | **0** | same WARN | 5 NDJSON lines, no truncation field |
| either, complete result | 3 events | 0 | none | no truncation field |

Truncation is stderr-only, absent from JSON, and invisible to exit-code
checks. Confirmed exactly as drafted.

### 2. The fix as drafted would NOT have caught the near-miss that motivated it

This is the finding that changes the work order.

`serial`'s truncation predicate is `state.serialRowsEmitted >= options.limit`
(`tools/telemetry:1800`, via `formatTruncationWarning` at
`tools/telemetry:825`), and `serialRowsEmitted` is incremented only for entries
that survive the `--grep` filter. The processing order is: reject non-serial
entries (`tools/telemetry:1842`), apply `--grep` (`:1843`), apply the emitted-row
cap (`:1844`), increment only survivors (`:1845-1846`). Codex independently
confirmed this ordering. A `--grep` run whose match count is below `--limit`
therefore trips no truncation warning on any channel, however much of the
window went unfetched.

Reproduced against a schema-legal 200-event window (distinct timestamps, needle
on the oldest line), at `--limit 1`:

```
telemetry serial Probe-Dev-01 --start … --until … --json --limit 1 --grep NEEDLE
  exit 0 | stdout: (empty) | stderr: (empty)
```

Empty stdout, **empty stderr**, exit 0 — the "confirmed absent" reading, over a
window where the needle is present and only 1 of 200 events was ever fetched
(see finding 5 for why paging halts). The same window at `--limit 5` finds it.

**Scope of the silent case, stated precisely.** On the `serial` path this
silent-false-absent is reachable at `--limit 1` only; traced query counts show
`--limit 2`, `5`, and `25` all fetch the full 200-event window. The everyday
route to the near-miss as described is `timeline`, which has no backward
paging and hard-caps at `--limit`: a 200-event window at the default `--limit
25` returns `count: 25`, exit 0, no JSON flag — a consumer grepping that stdout
has searched 25 of 200 lines and been told nothing.

**Consequence for the fix:** a `truncated` field derived from the existing
`serialRowsEmitted >= limit` predicate would report `truncated: false` and exit
0 on the `--limit 1` query above. The drafted acceptance criteria would all
pass while that case survived. The predicate must be based on **how much data
was fetched**, not on how many rows survived filtering.

### 3. `serial --json` is NDJSON with no envelope

`formatSerialEntry` (`tools/telemetry:1856-1866`) emits one standalone JSON
object per entry; there is no enclosing document. There is no existing
top-level place to put a `truncated` field, so the drafted instruction "every
`--json` output path must include an explicit `truncated` field in the JSON
itself" is not directly implementable for `serial` without deciding on a new
record shape. `timeline --json` is the opposite case: `outputTimeline`
(`tools/telemetry:1689-1693`) prints a single envelope, so the field drops in
cleanly there.

Qualification (from Codex, verified): the `timeline` envelope is **not** the
same on both paths. The DynamoDB fallback builds it locally with
`deviceId`/`start`/`end`/`count`/`events`/`source` (`tools/telemetry:792-799`),
but the HTTP path returns the lambda's payload **verbatim**
(`tools/telemetry:770-781`), and that payload carries only
`deviceId`/`start`/`end`/`count`/`events` — no `source`
(`lambda/src/query/timeline.ts:65-71`). Implementation consequence: `truncated`
must be **injected CLI-side into the HTTP payload**, not assumed to be
constructed locally, or the field will be missing exactly when a webhook secret
is configured.

### 4. `truncated` and "complete" currently overlap at the boundary

`formatTruncationWarning` (`tools/telemetry:825-831`) tests `eventCount >=
limit`, so a genuinely complete result of exactly `limit` events is reported
as truncated. Observed: a dataset of exactly 5 events with `--limit 5` emits
the WARN. Under the drafted rule 2 that result would exit non-zero, directly
contradicting the drafted criterion that a complete result is unaffected.

Requesting `limit + 1` and trimming to `limit` makes the distinction exact and
is implementable entirely CLI-side on both the DynamoDB and HTTP paths.
Detecting it via the query API instead would require a server change:
`queryDeviceEvents` (`lambda/src/storage/dynamo-read.ts:29-45`) passes
`Limit: limit` straight through and `handleTimelineQuery`
(`lambda/src/query/timeline.ts`) returns only `count` — no
`LastEvaluatedKey`, no more-available signal. That is out of scope for a
standalone CLI work order.

### 5. A second, separate defect: backward paging halts at `--limit 1`

`fetchWatchTimeline` (`tools/telemetry:1982-2004`) pages backward by setting
`pageEnd` to the oldest event's `eventTime` and breaking when that `pageEnd`
has already been visited. Because the key condition is `BETWEEN :start AND
:end` — **inclusive** — the boundary event is returned again on the next page.
At `--limit 1` that page is trivially full and its oldest event *is* the
boundary event, so `pageEnd` never advances and paging halts. Traced:

```
QUERY end=00:00:01.000 limit=1 -> 1 items [evt-0000]
QUERY end=00:00:00.000 limit=1 -> 1 items [evt-0000]     <- same event, halt
```

1 unique event fetched from a 200-event window. This is the mechanism behind
finding 2's silent case.

My original draft attributed this to bursts of events sharing one `eventTime`.
**That was wrong** — Codex correctly pointed out the `(deviceId, eventTime)`
key schema (`infra/lib/infra-stack.ts:30-32`) makes duplicate timestamps
impossible for a single device. `--limit 1` is the reachable route.

At `--limit >= 2` paging completes, but inefficiently: the re-returned boundary
event means each page yields only `limit - 1` new events, so `--limit 2` took
**200 queries** to walk a 200-event window. At that limit the boundary
duplicate also reaches output — the same event was emitted twice as two
identical NDJSON lines, because `collectNewTimelineEvents`
(`tools/telemetry:2104-2108`) dedupes against `state.seenEventIds`, which is
still empty when a single fetch batch is filtered.

**None of this is fixed by this WO** — see Scope. This WO makes such windows
*report* as truncated so the failure is loud; the halt, the O(n) query
amplification, and the duplicate emission go to a follow-up WO.

### 6. Exit-code space and blast radius

`OperatorError` defaults to exit 1 (`tools/telemetry:2400-2402`); exit 2 is
used by `failAmbiguous` (`tools/telemetry:2392`). No other non-zero code is in
use, so **3 is free**. Neither `timeline` nor `serial` calls `process.exit`
on truncation today — both return normally.

Nothing in `scripts/`, `.github/`, or `docs/` invokes `tools/telemetry` and
checks its exit code; the only in-repo references are `tools/commit.test.sh`
(which stubs the file, not the CLI) and documentation prose. The breaking
change therefore lands only on external/agent consumers.

Baseline: 137 tests pass (`node --test tools/telemetry.test.js`) as of
`f3fbfc6` (PR #16, WO-2026-08-05-001's regression tests). That PR touched
`tools/telemetry.test.js` only, so every `tools/telemetry:NNN` reference in
this document is against current `main`.

## Design Decisions (approved by Chip, 2026-08-27)

1. **Fetch-based truncation predicate.** Detect truncation from what was
   fetched, not from post-filter emitted rows. Required for finding 2.
2. **Serial signals truncation in a trailing summary record.** Existing
   NDJSON data-line shape is unchanged; one extra discriminated record is
   appended.
3. **Exit code 3**, distinct from 1 (generic error) and 2 (ambiguous
   selector), so consumers can tell "truncated but valid data on stdout" from
   "hard failure, no data".
4. **The paging defect (finding 5) is detected here, fixed in a follow-up
   WO.** This WO does not touch the paging loop's termination conditions
   beyond reporting whether it stopped early.

## Scope

### 4.1 `timeline`

- Request `limit + 1` records and trim the response to `limit`. Set
  `truncated = (fetched > limit)`. `count` and `events` must reflect the
  trimmed set — never emit `limit + 1` events.
- Applies to both paths: `queryTimelineFromDynamo` /
  `queryTimelineRecordsFromDynamo` (`tools/telemetry:832-868`) and the HTTP
  path in `fetchTimeline` (`tools/telemetry:751-780`).
- HTTP edge case: `parseQueryParams` clamps `limit` to `maxLimit: 1000`
  (`lambda/src/query/timeline.ts`), so above that clamp the `+1` probe cannot
  distinguish. **Compare against the effective server cap, not the requested
  limit:**

  ```js
  const probeLimit = Math.min(requestedLimit + 1, TIMELINE_HTTP_MAX_LIMIT);
  truncated = events.length > requestedLimit
    || events.length >= TIMELINE_HTTP_MAX_LIMIT;
  ```

  A genuinely complete window of exactly 1000 events then reports `truncated:
  true` — a conservative false positive in the safe direction; document it in
  `docs/API.md`. This must be explicit in code and covered by a test.

  > **Corrected 2026-08-27.** This bullet originally specified a `count >=
  > limit` fallback for `limit >= 1000`. That rule is defective and cannot
  > work: the server clamps to 1000, so `count` can never reach a `limit`
  > above 1000, and `--limit 1001` over a 5000-event window reported
  > `truncated: false`, exit 0. See Amendments below.
- `timeline --json` envelope gains `truncated: true|false`. Adding `limit`
  alongside it is permitted and encouraged; nothing else in the envelope
  changes.
- **The HTTP path returns the lambda payload verbatim
  (`tools/telemetry:770-781`).** `truncated` must be injected into that payload
  CLI-side. Do not assume the envelope is constructed locally — it is only on
  the DynamoDB path (finding 3).

### 4.2 `serial`

Truncation for `serial` has **two** independent sources and either one must
set `truncated: true`:

- **Fetch capped.** `fetchWatchTimeline` must report whether it stopped while
  more data remained. Breaking at the `visitedPageEnds` guard
  (`tools/telemetry:1987`) *after a full page* means data remained
  unfetched → truncated; this is the `--limit 1` halt of finding 5. Breaking
  because a page came back short (`tools/telemetry:1997`) means the window was
  exhausted → not truncated. Breaking because the cursor was reached
  (`tools/telemetry:2000`) means caught up → not truncated. Return this as a
  flag alongside `events`; existing callers that ignore it must keep working.
- **Emission capped.** `buildSerialEntries` skips entries once
  `!options.follow && state.serialRowsEmitted >= options.limit`
  (`tools/telemetry:1844`). Count those skips and treat any skip as
  truncated.

Output:

- `serial --json`, non-`--follow` only: after all data lines, emit exactly one
  trailing NDJSON record with a discriminator, e.g.
  `{"record":"summary","truncated":true,"count":<emitted>,"limit":<limit>}`.
  Existing data-line shape is **unchanged** — do not add fields to data lines.
- `serial` without `--json`: stdout unchanged.
- `--follow` runs never terminate normally and must not emit the summary
  record or a truncation exit code.

### 4.3 Exit code

- On truncation, exit **3** — after all output has been written to stdout.
  The data must still be emitted; exit 3 means "this result is partial", not
  "this result is absent".
- Applies whether or not `--json` was passed.
- Complete results continue to exit 0.

### 4.4 stderr

The existing `WARN: results truncated at N events (--limit), narrow your
window or raise --limit.` message is **preserved, not replaced** — this WO
adds a machine-readable signal alongside the human-readable one.

Note for verification: under the new predicate this warning will now also fire
on runs where it previously stayed silent (notably `--grep` runs over
truncated windows, per finding 2). That broadening is **intended and
required**, not a regression — the message text is what must stay stable, not
the set of conditions that trigger it.

### 4.5 Explicitly out of scope

- `watch` — `--limit` there is a per-poll page size for a continuous tail,
  not a terminal result cap; a tail has no "complete" state to report. No
  changes.
- `fleet --activity-limit` — a display cap (`.slice(0, limit)`,
  `tools/telemetry:1553`) applied to an already-complete device inventory,
  not a query-window truncation. No changes.
- `devices`, `device` — no `--limit`. No changes.
- The paging under-fetch of finding 5. No changes to the termination
  conditions themselves.
- `lambda/` — no server-side change. The `+1` probe is CLI-side only.

## Acceptance Criteria

- `timeline --json` over a window exceeding `--limit` produces `truncated:
  true` in the JSON envelope and exit code 3, confirmed by an actual CLI run,
  not code inspection. `count` equals `limit`, not `limit + 1`.
- `serial --json` over a window exceeding `--limit` produces a trailing
  summary record with `truncated: true` and exit code 3, confirmed by an
  actual CLI run.
- **The motivating near-miss is closed:** `serial --limit 1 --grep <pattern>`
  over a multi-event window reports `truncated: true` and exits 3 *even when
  the grep matches zero lines* — today this returns empty stdout, empty
  stderr, exit 0. This is the criterion the drafted WO would have missed; it
  must be demonstrated against a real truncating query.
- A complete, non-truncated result is unaffected: `truncated: false`, exit 0,
  stdout byte-identical to current behavior apart from the added
  `truncated` field (timeline) / trailing summary record (serial).
- A complete result of **exactly `limit`** events reports `truncated: false`
  and exits 0 — the current false positive is gone.
- The stderr WARN still appears on truncated results, text unchanged.
- `--follow` behavior is unchanged: no summary record, no truncation exit
  code.
- `watch`, `fleet`, `devices`, `device` behavior unchanged.
- All 137 existing tests still pass, unmodified.

## Required Tests

Add to `tools/telemetry.test.js`. Tests must exercise real code paths with
mocked `awsJson`/`fetch` (the established pattern in this file), not assert on
hand-built fixtures:

1. `timeline`, DynamoDB path: window larger than `--limit` → `truncated:
   true`, `count === limit`, `events.length === limit`.
2. `timeline`, DynamoDB path: window smaller than `--limit` → `truncated:
   false`.
3. `timeline`, DynamoDB path: window of **exactly** `--limit` events →
   `truncated: false` (boundary regression for finding 4).
4. `timeline`, HTTP path: asserts the outgoing URL requests `limit + 1`, and
   that a full response yields `truncated: true` with a trimmed event list.
5. `timeline`, HTTP path: limits **above** the server clamp (e.g. `--limit
   1001`) over a window larger than 1000 → `truncated: true`. Exactly `--limit
   1000` → `truncated: true` (the documented conservative case).
6. `serial`, emission-capped: more serial rows in the window than `--limit`
   → trailing summary record with `truncated: true`.
7. **`serial --limit 1 --grep <no-match>` over a multi-event window →
   `truncated: true`.** The near-miss regression test. Must fail against
   current `main` (which returns empty stdout, empty stderr, exit 0). Fixture
   timestamps must be distinct and fixed — see the methodology note in the
   findings; a fixture with duplicate `eventTime` values per device is not
   schema-legal and will not exercise the real path.
8. `serial --limit 25 --grep <no-match>` over a fully-fetched window →
   `truncated: false` (guards against the fix over-reporting; traced query
   counts confirm `--limit >= 2` fetches the whole window today).
9. `serial --follow` → no summary record emitted.
10. Exit codes, via the existing `runTelemetry()` subprocess helper or an
    equivalent end-to-end harness: truncated → 3, complete → 0, genuine error
    → 1 (unchanged), ambiguous selector → 2 (unchanged).
11. stderr WARN text preserved on a truncated run.
12. Existing 137 tests pass unchanged.

For tests 1–9 the mocked layer must model pagination faithfully (return
`LastEvaluatedKey` while more records remain), otherwise the `+1` probe and
the fetch-capped detection are not actually being exercised.

## Follow-up

File a separate WO for finding 5, covering three related defects in
`fetchWatchTimeline`'s backward paging, all caused by the inclusive
`BETWEEN :start AND :end` boundary re-returning the previous page's oldest
event:

1. At `--limit 1`, paging halts after one event and silently under-fetches the
   window.
2. At `--limit >= 2`, each page yields only `limit - 1` new events — `--limit
   2` issued 200 DynamoDB queries to walk a 200-event window.
3. The re-returned boundary event can be emitted twice, as two identical
   NDJSON lines, because `collectNewTimelineEvents` (`tools/telemetry:2104`)
   dedupes against `state.seenEventIds`, which is empty while a single fetch
   batch is being filtered.

After this WO, case 1 reports as truncated rather than failing silently; cases
2 and 3 are untouched.

## Amendments (2026-08-27, during implementation)

Four things this work order got wrong or failed to anticipate. Recorded because
the same mistakes are available to the next WO touching bounded queries.

### 1. The HTTP fallback rule was defective (spec error)

Scope 4.1 originally specified `count >= limit` when `limit >= 1000`. That rule
cannot work — the lambda clamps to 1000, so `count` never reaches a larger
`limit`. Copilot implemented the spec faithfully and `--limit 1001` over a
5000-event window reported `truncated: false`, exit 0: precisely the defect this
WO exists to eliminate, introduced by this WO's own text. Corrected inline
above. **A truncation rule must compare against the cap that actually bound the
result, not the one the caller asked for.**

### 2. The internal DynamoDB row cap was never considered

`WATCH_DYNAMO_MAX_ROWS = 2000` (`tools/telemetry:27`) caps
`queryTimelineRecordsFromDynamo` below the `limit + 1` probe point, so at
`--limit >= 2000` the probe row is never fetched. `--limit 5000` over a
2500-event window returned 2000 events and reported complete. The investigation
traced the probe against the *requested* limit and never asked what other caps
sat between it and the data.

Correct signal: `truncated = records.length > requestedLimit || moreAvailable`,
where `moreAvailable` is whether `exclusiveStartKey` survived the paging loop.
Note the first attempt at this used `records.length >= maxRows`, which conflates
"filled the cap" with "more remains" and made a *complete* exactly-2000 window
report truncated.

### 3. Truncation detection had to reach the serial path too

Scope 4.2 specified serial's two truncation sources but assumed the timeline
fixes would cover the shared fetch layer. They did not: `fetchWatchTimeline`
discarded the page-level flag and `fetchTimelinePage`'s HTTP branch computed
none, so `serial --limit 3000` reported complete on a window where `timeline
--limit 3000` correctly reported truncated — the same window, the same limit,
two different answers.

The converse then bit as well: propagating the page flag unconditionally made
every multi-page serial window report truncated, because "this page has more
behind it" is the normal state of every intermediate page. The correct gate is
`page.truncated && pageEvents.length < limit` — a full page means the loop will
fetch the rest, a short page with data remaining means a cap blocked it.

### 4. Protected paging is protected in behavior, not just in syntax

Scope forbids changing `fetchWatchTimeline`'s termination conditions. An attempt
to probe the HTTP page path with `limit + 1` left the break expressions
untouched but changed their *inputs* — the extra event altered `pageEvents.length`
and `oldest`, so the loop stopped at a different point, on a path `watch` also
uses. Probe wider, expose narrower: trim before the protected loop sees it.

### The pattern underneath all four

Every defect in this WO's implementation was the same confusion: **"we hit a
cap" and "more data remains" are not the same fact.** Caps appear at four
levels here — per-page, per-window, internal (`WATCH_DYNAMO_MAX_ROWS`), and
server (`maxLimit`) — and a predicate that is right at one is not automatically
right at the others.

The test consequence, which cost two review rounds: a truncation predicate
needs a **complete-case** test on both sides of every cap it can trip on. Each
round's suite passed fully while the defect was live, because every round added
truncated-case coverage and no complete case at the new boundary.
