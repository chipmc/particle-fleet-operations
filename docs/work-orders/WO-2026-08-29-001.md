# WO-2026-08-29-001: `timeline`/`serial` over HTTP — bounded windows and cross-format correctness

**Status:** Drafted. Not dispatched. **Blocked** — see Sequencing.
**Split from:** WO-2026-08-28-004 / PR #20, which was scoped down to its verified DynamoDB
work after five Copilot rounds and two in-house commits.
**Blocked on:** WO-2026-08-28-003 **Part A and Part B**. Not Part A alone — see Sequencing.

## Why this is its own work order

PR #20 fixed the paging boundary, the cross-format omission and the consolidation on the
**DynamoDB** transport, all independently confirmed. Every attempt to carry the same fix to
the **HTTP** transport failed, across five review rounds and two in-house commits. The
reason is structural rather than a sequence of implementation mistakes:

**The CLI cannot control the bound the server actually queries.** The widen-and-filter
approach depends on sending a bound in a specific lexicographic form. The query API
re-normalises what it receives (`lambda/src/query/timeline.ts`), so the low-sort form the
widening relies on does not survive. A client-side fix is not available while the stored
`eventTime` encodings remain mixed.

That is why this is sequenced behind the canonicalisation work rather than retried again.

**Final HTTP state at PR #20 merge (2026-09-02).** Both HTTP cells were measured against

| cell | `main` | PR #20 |
|---|---|---|
| dense window, `timeline`/HTTP | 0/6, `truncated:true`, 1 request | identical |
| dense window, `serial`/HTTP | 0/6, `truncated:false`, 42 requests | identical |

The `serial`/HTTP cell is the worse of the two and should be this WO's first target: it
returns **zero of six** in-window rows with `truncated:false` and exit 0 — a silent total
loss, the failure class WO-2026-08-28-004 was opened to eliminate, still live here because
it cannot be fixed from the CLI while encodings stay mixed (defect 3).

Seven annotated skips in `tools/telemetry.test.js` carry the HTTP cases. None of them
covers a DynamoDB behaviour.

### 1. Dense windows lose every in-window row on timeline/HTTP — RESOLVED at `bd4f6ff`

With ~1,994 widened spill rows ahead of six in-window rows:

| dataset | timeline/Dynamo | serial/Dynamo | serial/HTTP | timeline/HTTP |
|---:|---:|---:|---:|---:|
| 2,000 | 6/6 | 6/6 | 6/6 | **0/6** |
| 5,000 | 6/6 | 6/6 | 6/6 | **0/6** |
| 8,000 | 6/6 | 6/6 | 6/6 | **0/6** |

`fetchTimeline` consumes a single `fetchTimelinePage` result while the HTTP page helper
stops at its 1,000-row cap and only returns `nextPageEnd`. Zero rows returned for a window
with six matches is this WO chain's defining failure mode, still live on that one cell.

### 2. The HTTP page helper ignores the raw-scan budget — RESOLVED at `bd4f6ff`

`maxRows` is forwarded and honoured on the DynamoDB branch. The HTTP branch ignores it and
reports only the final retry's `rawCount`, hiding earlier enlarged requests. On a 5,000-row
dense fixture the nominal budget was 1,025 rows; the helper fetched
`25+50+100+200+400+800+1000` twice = **5,150 raw rows**.

### 3. The server re-normalises the bound

The widened low-sort start (`...000000+00:00`) does not survive Lambda normalisation, and
widened ends can be rejected as future. This is the blocking one: it cannot be fixed from
the CLI.

### 4. `--hours`/default cannot simply be routed through the shared query

Attempted in PR #20 commit `0605718` and reverted in `6b33226`. Replacing the `hours=`
request with an explicit range **silently removes the Lambda's 168-hour cap** —
`maxHours: 168` validates only the `hours` parameter
(`lambda/src/utils/query-params.ts`). Verified: `--hours 169` was accepted with no
duration limit. Any future attempt must preserve that validation.

### 5. Complete results can report `truncated: true` on HTTP

A complete window reports truncated when the raw budget is exhausted reading rows outside
it. This contradicts WO-2026-08-27-001 and `docs/API.md:624-626`, where the only sanctioned
conservative case is the 1,000-row clamp. Returning `false` at exhaustion is **not** a fix —
it trades this false positive for false negatives, because a bounded scan cannot distinguish
two datasets sharing a scanned prefix where only one has an unscanned in-window row.
Currently carried as an annotated skip in `tools/telemetry.test.js`.

## Sequencing — and why Part A alone is insufficient

**WO-2026-08-28-003 Part A** canonicalises `eventTime` at ingest. That fixes *future* rows
only. **Part B**'s backfill is what resolves the historical rows that already carry mixed
encodings, and those are exactly the rows an evidence tool queries. Until both have landed,
defects 1–3 are being worked around rather than fixed.

An earlier annotation in PR #20 named Part A alone as the resolution. That was wrong and is
corrected here and in the test comment (Codex, PR #20, 2026-08-28).

Recommended order: **003 Part A → 003 Part B → this WO.**

## Verification requirements

### Fixture parameters are set by the reviewer, not the implementer

**This is a process requirement, not a suggestion.** Three separate times in this WO chain,
a verification fixture chosen by whoever wrote the code was too small to reach the defect it
was meant to catch:

1. A four-cell dense test used **four** spill rows; the defect needs ~2,000. It passed while
   timeline/HTTP returned 0 of 6 rows.
2. A query-count bound was **doubled** to accommodate the implementation, hiding a budget
   that scanned ~4,000 raw rows against an intended 2,025.
3. An R1 test used a **mixed-format** row pair, where the defect does not reproduce, and so
   passed against the code containing it.

Two of those three were the reviewer's own work, so this is not about who is implementing.
Self-selected test parameters are a predictable blind spot: the person who knows how the
code works picks values it handles. Remove it structurally rather than by being more careful.

For this WO the reviewer specifies, before implementation begins:
- dataset sizes and **spill-row counts** for every dense-window case
- the timestamp **encodings** present in each fixture, including same-second interleaving
  and rows landing exactly on a second boundary
- the `--limit` values, including 1 and values at and above the 1,000 server clamp
- the expected row **counts and identities**, not just the truncation flag

An implementer may add cases but may not narrow, resize, or re-encode a specified one. Any
bound that needs widening to pass is a finding to report, not an edit to make.

### Gates
- All four `{timeline, serial}` × `{Dynamo, HTTP}` cells for every behaviour, with results
  stated per cell. A fix verified on one transport is not verified.
- WO-2026-08-27-001's full truncation matrix.
- WO-2026-08-28-004's 34-cell matrix.
- Every new test must be shown to **fail** against the pre-fix revision, with output pasted.
- Any harness or mock must be cross-checked against the live table before its results are
  used as evidence. A mock modelling DynamoDB `ExclusiveStartKey` as a positional offset
  rather than a key produced two false blocking defect reports across two review rounds in
  WO-2026-08-28-004.
