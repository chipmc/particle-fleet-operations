  The only 67 in fleet-ops' data was an unrecorded working query: Dev-09's log lines for 2026-10-12 04:55–06:10 UTC, a different window. Its source in the firmware thread is unconfirmed.
- **Why the three lines are absent** (firmware v41 at `caf6760` (source identical to `4b86550` except the version string); AWS rows as cited):
  - **`Config:` and `LedgerCallback`:** `connectionMode` 0 was applied the evening before. On 2026-10-12 at 14:07:47 `LedgerCallback: kind=input ledger=device-settings`, then at 14:07:50 `Config: Connection mode -> CONNECTED`. At the 22:00 boot the stored value already matched. `Config: Connection mode` logs only on a change (`ConfigApply.cpp:449-454`), and `LedgerCallback` only when an input ledger syncs (`LedgerClient.cpp:48-62`). Neither happened.
  - **`ConfigHold: ended`:** it prints only inside `areLedgersSynced()` (`LedgerClient.cpp:152-153`). Its callers are the sleep gate (`State_Sleep.cpp:511`) and the config-failure path (`State_Connect.cpp:557-566`). The device went Connect→Idle at uptime 15.8 s and its sleeps were aborted in open hours, so neither path ran.
- **`THRASH`:**
  - Idle has no `THRASH` timeout (`ThrashGuard.cpp:59-75` returns 0), but the no-progress clock keeps running from the last mark (`QUEUE_DRAIN`, uptime about 21.8 s).
  - At Idle→Sleep the Sleep limit is 60 s, so the trip fires at once with `noprog=1412s`. The next one, Idle→Report at 23:00 (limit 120 s), shows `noprog=2169s`.
  - All four trips through 00:42 were tier 1 (log and back off).
  - `TimeDiag` never marked progress, so its change to log-only-on-change (`a745ba1`) did not cause these trips.
