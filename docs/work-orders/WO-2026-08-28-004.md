# WO-2026-08-28-004 — Paging boundary fix + cross-format defensive fetch (combined)

**Status:** Complete 2026-09-02. Defect 1, Defect 2 (DynamoDB) and the consolidation are
closed and verified against `main`. Step 0 retired — see Implementation Status. The HTTP
transport is WO-2026-08-29-001.
**Supersedes / merges:** WO-2026-08-28-001 (paging re-fetch), WO-2026-08-28-003 Part C (defensive CLI)
**Depends on:** WO-2026-08-28-003 Part A (ingest-time `eventTime` normalization) should land first — see Sequencing.
**Blocks:** WO-2026-08-28-003 Part B (backfill) is independent of this WO but should not be treated as a substitute for it.
**Touches:** the fetch/paging loop protected by PR #18's six-round truncation matrix (`0f70dbd`, `main`).

## Why combined

Both source WOs modify the same fetch/paging loop:

- WO-001 changes the `BETWEEN` boundary handling (inclusive-inclusive → needs an exclusive re-derivation of the page cursor).
- WO-003-C changes what that same loop does with a boundary `eventTime` when formats can still be inconsistent (defensive handling for any pre-backfill or malformed rows).

Each of these WOs independently triggers the requirement (stated in WO-001) that anyone touching this loop re-run PR #18's full truncation matrix, not just the criteria specific to their own change. Landing them separately means paying that six-round-class validation cost twice, with a real chance the second change silently reopens something the first change just proved closed — the exact failure shape this whole arc has been about. Landing them together means one loop change, one validation pass.

## Investigation notes (verified against the live table, added post-draft)

1. **The moving bound is the upper one, not the lower.** Paging in this loop runs *backward*: `pageEnd` starts at the window end and walks down while `:start` stays fixed. A fix worded as "the next page's lower bound is exclusive of the last row returned" describes the wrong variable — an implementer following that literally would modify `:start` and leave Defect 1 untouched. The fix must operate on `pageEnd`.

2. **Normalization to a comparable form cannot fix Defect 2 by itself — this is load-bearing, not a wording nitpick.** The `BETWEEN` comparison happens server-side inside DynamoDB against the stored string key. A client-side parsed epoch value cannot be sent as a query bound; only a string can, and against mixed-format data **no bound string is correct at both ends simultaneously**:

   | bound | as `.NNNZ` | as `.NNNNNN+00:00` |
   |---|---|---|
   | `:start` | under-includes (data loss) | over-includes (safe) |
   | `:end` | over-includes (safe) | under-includes (data loss) |

   Because the two formats only interleave within a single second, the robust rule is: **widen the query to whole-second boundaries** (a string bound that is safe — i.e. over-inclusive — against both formats), then **filter client-side on parsed instants** to recover exact semantics. Over-inclusion is recoverable by filtering; under-inclusion is not recoverable at all once the query has already excluded the row.

   **Consequence for truncation accounting:** PR #18's truncation counts must be computed *after* the client-side filter, not from the raw widened-query result — otherwise a widened fetch reports row/truncation counts that don't correspond to what the caller's window actually asked for, which is its own version of "reports something other than what was returned."

3. **Test fixtures must contain both timestamp formats.** A single-format fixture set cannot exercise Defect 2 at all — it will pass green with the defect fully live, the same shape as the coverage gaps across rounds 2–5 of PR #18. Any fixture used to validate this WO must include rows from both `serialLog` (`.NNNNNN+00:00`) and `pdiag`/webhook (`.NNNZ`) producers, with at least one pair positioned to interleave within the same second as in the `Boron-Dev-09` case.

4. **"Whole-second boundaries" is underspecified — the *format* of the widened bound still matters.** Flooring `:start` to `.000Z` reintroduces the same defect one level up: a microsecond row sitting exactly on that second boundary is still dropped. Verified by direct comparison against both representations of the same instant:

   | widened bound | `.000000+00:00` row on the boundary | `.000Z` row on the boundary | verdict |
   |---|---|---|---|
   | `:start = ...40.000Z` | excluded | included | **drops a row** |
   | `:start = ...40.000000+00:00` | included | included | safe |
   | `:end = ...41.000Z` | included | included | safe |
   | `:end = ...41.000000+00:00` | included | included | safe |

   So the rule is directional, not merely "round to the second": floor `:start` using the **lowest-sorting** representation of that instant (`.000000+00:00`), and ceil `:end` to the next second (either representation is safe there). Implementing "round to whole seconds" with `toISOString()` — which emits `.000Z` — would leave Defect 2 live at every second boundary while appearing to fix it, and a fixture whose rows never land exactly on a second boundary would not catch it.

## Defect 1 — inclusive `BETWEEN` boundary re-fetches / halts

**Root cause:** the page query uses an inclusive bound on both ends of `eventTime`. Every page after the first re-returns the previous page's oldest row as its first result.

**Confirmed via query trace** (`--limit 5`): `evt-0004`, `evt-0008`, `evt-0012` each fetched twice.

**Consequences, measured against a 200-row window:**

| `--limit` | queries observed | ideal | 
|---|---|---|
| 1 | 2 (halts after 1 row fetched) | 200 |
| 2 | 200 | 100 |
| 5 | 50 | 40 |
| 25 | 9 | 8 |

The `--limit 1` case is the one that loses data — it doesn't just re-fetch, it halts. Amplification at other limits is a performance defect, not a correctness defect; negligible at the default (25), pathological below 5.

**Scope note:** PR #18 already stops duplicate rows from reaching CLI output. This defect is upstream of that — it's about what gets *fetched*, not what gets *displayed*. A dedup at the display layer can mask this defect's symptom (duplicates) while leaving its consequence (the `--limit 1` halt) untouched.

**Fix direction:** re-derive `pageEnd` (the upper/walking bound — see Investigation note 1) so it excludes the last row already returned, rather than reusing that row's raw `eventTime` as an inclusive bound. `:start` is not the moving bound and should not be the target of this fix. Needs to compose correctly with Defect 2's fix (see Interaction below) — the cursor is an `eventTime` string, and Defect 2 is about what `eventTime` strings can look like pre-backfill.

## Defect 2 — cross-format `eventTime` causes silent omission (not truncation)

**Root cause:** `extractTimestamp` passes each producer's timestamp string through verbatim into the DynamoDB string sort key (`eventTime`). Producers disagree on format:

- `serialLog`: `.NNNNNN+00:00` (microsecond precision, offset notation)
- `pdiag` / webhooks: `.NNNZ` (millisecond precision, Zulu notation)

Both are valid ISO 8601. Neither sorts lexicographically against the other (`'8' < 'Z'` inverts events that are chronologically in the opposite order).

**Confirmed live** on `Boron-Dev-09`:

```
2026-08-27T13:09:40.397Z          pdiag      ← earlier
2026-08-27T13:09:40.397813+00:00  serialLog  ← 0.813 ms later
```

**Confirmed consequence**, run against the real table:

```
--start 13:09:40.397Z   → serialLog row at .397813 MISSING
--start 13:09:40.396Z   → serialLog row at .397813 present
```

An event 0.813 ms inside the requested window is silently omitted. `exit 0`, no flag, no warning.

**Why this is a distinct failure class from what PR #18 fixed:** PR #18's truncation detection catches "more rows exist than the page/window returned." This defect produces *zero* rows for a query that should have matched — nothing was truncated, the query simply didn't match the row that was there. The existing truncation machinery is structurally blind to it. The same lexicographic mismatch can also drop rows mid-page, since the page cursor (`pageEnd`) is a raw `eventTime` string.

**Fix direction (defensive, CLI-side only — this WO does not do ingest normalization):** per Investigation note 2, there is no single bound string that is correct against mixed-format data — this rules out "normalize to a comparable form before sending as a query bound" as a fix, since the bound sent to DynamoDB must remain a string compared server-side. Instead: **widen the server-side query to whole-second boundaries** (over-inclusive, therefore safe, against both known formats), then **filter the returned rows client-side on parsed instants** to recover exact window semantics. `pageEnd`/`:start` cursors passed to the next query must also go through this widen-and-filter treatment, not a raw string comparison. Truncation/count accounting (per PR #18) must be computed from the post-filter result set, not the raw widened fetch. Do not silently truncate sub-millisecond precision when parsing for the client-side filter — that decision belongs to WO-003 Part A (ingest-time canonical format), not to this defensive layer. This WO's fix is post-hoc and must keep working correctly on data written both before and after Part A lands.

## Interaction between the two defects

Both defects live in the same boundary-handling code: Defect 1 is about *inclusivity* of the bound, Defect 2 is about *comparability* of the bound. A fix that solves inclusivity without also solving comparability will still drop cross-format rows sitting near a page boundary. A fix that solves comparability without also solving inclusivity will still halt at `--limit 1`. **Both must be fixed in the same change**, verified together — this is the primary reason for combining the WOs rather than a scheduling convenience.

## Sequencing

Recommended: **WO-003 Part A (ingest normalization) → this WO → WO-003 Part B (backfill)**, with WO-002 (`watchEventId` identity contract) held until after Part A settles the canonical `eventTime` format.

This WO's fix must be correct on the *pre-normalization* data that will exist during the gap between Part A shipping and Part B's backfill completing — i.e., it can't assume Part A has already run everywhere. Landing this WO before Part A is also acceptable and arguably safer (defends against cross-format rows regardless of whether/when normalization lands), but then Part A's rollout doesn't need to be coordinated with this WO's rollout. Landing this WO *after* Part A only reduces the surface area it needs to defend, it doesn't remove the requirement.

## Validation requirement

Per WO-001's original flag: this WO edits the loop PR #18 spent six review rounds protecting. Stage 7 must re-run **PR #18's full truncation matrix**, not just criteria specific to Defects 1 and 2, plus:

- Complete-case coverage at every independent boundary this loop can trip on: `--limit 1` halt, cross-format adjacent-timestamp windows, and page-boundary crossings where the boundary row's format differs from the query's `--start`/`--end` format.
- Explicit test: query window boundary set exactly at a cross-format collision point (as in the `Boron-Dev-09` case above), both inclusive and exclusive of the colliding row, both before and after Part A normalization is simulated.
- Explicit test: verify truncation/count fields reflect the post-filter result, not the widened raw fetch, when a whole-second widen pulls in rows outside the caller's requested window.
- **Explicit named test — "second-boundary instant, both `:start` flooring forms" (per Investigation note 4).** Fixture must contain a row timestamped *exactly* on a second mark in **each** format — `T13:09:40.000000+00:00` and `T13:09:40.000Z` — for the same device. Query with `--start` at that second, and assert **both rows are returned**, under each candidate flooring representation of `:start`:

  | `:start` flooring form | required result |
  |---|---|
  | `...40.000000+00:00` | both boundary rows returned |
  | `...40.000Z` | must be shown to DROP the `.000000+00:00` row — this is the failing case the fix must not ship |

  The second line is the point of the test: it must fail if the implementation floors with `toISOString()`. A test that only asserts the passing form would go green against an implementation that floors to `.000Z`, leaving Defect 2 live at every second boundary.

  This case is **not** covered by the same-second interleaving fixture required by Investigation note 3 — that fixture's rows land *within* a second, not *on* one — and it is not covered by the general complete-case coverage bullet above. It must exist as its own test.
- Per Investigation note 3: all fixtures used for this validation must contain both `eventTime` formats, with at least one same-second interleaved pair. A single-format fixture is not valid coverage for this WO regardless of how many cases it enumerates.
- Per the arc's standing lesson — a boundary predicate correct at one cap level isn't automatically correct at another. Each round of validation should add a *complete*-case test at whatever new boundary it introduces, not just a *truncated*-case test.

### Step 0 — retired from this WO, not deferred

Step 0's raw-scan budget and collected-event cap are **removed**. They were never a fix.
Every bound they imposed discarded the oldest rows *before* the exact-window filter and
`--grep` ran, and reported `truncated: true` on results that are complete — which
`docs/API.md:625` forbids on the DynamoDB path, where the only sanctioned conservative
case is the 1,000-row HTTP clamp.

Two bounds existed, not one:

1. The collected-event cap in `fetchWatchTimeline`. At `--limit 2000 --grep` over a
   2,500-row window where only the oldest 500 rows matched, it returned **0 rows,
   `truncated:true`** against `main`'s 500 rows, `truncated:false`.
2. An inner 2,000-row raw ceiling in `queryFilteredTimelineRecords`. This is what broke
   the dense `timeline` cell: a widened query deliberately admits out-of-window spill, and
   2,000 same-second spill rows exhausted the ceiling before the scan reached any
   in-window row. `serial` escaped it only because it pages across many calls.

Defect 1 does **not** depend on either. With both removed, query counts are exactly
`ceil(N/limit)` at every limit — the amplification Defect 1 addressed came from the
inclusive bound causing duplicate re-fetch, not from unbounded walking. What Defect 1's
fix does remove is `main`'s *accidental* work ceiling (it stopped when a page came back
short), which is a scale consequence, not a correctness one.

Five tests asserted the retired bounds and are rewritten to the `docs/API.md:625`
contract, with expectations derived from that contract rather than from current output.
No test was deleted.

### Known-open, carried by other work orders

- The HTTP transport: `timeline`/HTTP and `serial`/HTTP both return 0 of 6 on a dense
  window, bit-identical to `main`. Seven annotated skips. WO-2026-08-29-001.
- `serial`/`watch` **cursor**-adjacent cross-format rows on Dynamo: with the cursor at
  `.500Z`, a row at `.500500+00:00` is silently dropped at `--limit 1` (`truncated:false`,
  exit 0). `main` behaves identically, so it is not a regression — but it is Defect 2's
  signature on a path this WO did not close. It is the `--start`/`--until` window path
  that is fixed. Needs its own work order.

### Follow-on: query cost

Query work is now unbounded by design. A 10,000-row window at `--limit 25` costs 400
queries and returns all 10,000 rows, against 81 queries returning 2,000 of 10,000 before.
This is **not** unfinished work on this WO. The open item is: *evaluate whether
large-window query cost needs bounding, based on real fleet usage* — and any bound that
comes out of that must not repeat Step 0's mistake of discarding rows ahead of the filter.

### Method note

Four merge-gate passes were needed after the PR was already believed complete, and each
found a real, reproducible defect. Three of the four were instances of one pattern: a
bound on rows scanned, combined with filtering applied after the fetch, silently drops
matches outside the newest scanned slice. The pattern was only visible once the cells were
measured against `main` rather than against expected values, because several tests
encoded the bounded behaviour as if it were the contract.
