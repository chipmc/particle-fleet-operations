## Investigation Findings (2026-08-28)

Verified against `main` at `0f70dbd` by running the real CLI with a fake `aws`
executable on `PATH` that logs every `dynamodb query` it receives, so the claims
below are observed query traces, not inferences from source.

### 1. Root cause: the key condition is inclusive at both ends

`queryTimelineRecordsFromDynamo` queries `eventTime BETWEEN :start AND :end`
(`tools/telemetry:874`), and `fetchWatchTimeline` advances by assigning the
oldest row's timestamp directly to `pageEnd` (`tools/telemetry:2058`). Because
the bound is inclusive, **every page after the first re-returns the previous
page's oldest row.** Traced, `--limit 5` over 20 events:

```
QUERY end=00:00:01.000 limit=5 -> [evt-0000,evt-0001,evt-0002,evt-0003,evt-0004]
QUERY end=23:56:00.000 limit=5 -> [evt-0004,evt-0005,evt-0006,evt-0007,evt-0008]
QUERY end=23:52:00.000 limit=5 -> [evt-0008,evt-0009,evt-0010,evt-0011,evt-0012]
QUERY end=23:48:00.000 limit=5 -> [evt-0012,evt-0013,evt-0014,evt-0015,evt-0016]
QUERY end=23:44:00.000 limit=5 -> [evt-0016,evt-0017,evt-0018,evt-0019]
```

`evt-0004`, `evt-0008`, `evt-0012` and `evt-0016` are each fetched twice. Each
page yields `limit - 1` new rows, not `limit`.

### 2. `--limit 1` halts after one row

At `--limit 1` the page is trivially full and its oldest row *is* the boundary,
so `pageEnd` never advances and the `visitedPageEnds` guard
(`tools/telemetry:2041`) stops paging. Traced over a 200-event window:

```
QUERY end=00:00:01.000 limit=1 -> [evt-0000]
QUERY end=00:00:00.000 limit=1 -> [evt-0000]     <- same row, guard fires
```

**1 of 200 rows fetched.** WO-2026-08-27-001 made this safe rather than silent —
the run now reports `truncated: true` and exits 3 — but the window is still not
read.

### 3. Query amplification at small limits

Queries scale as `N / (limit - 1)` instead of `N / limit`. Measured over a
200-event window:

| `--limit` | queries issued | ideal | overhead |
|---|---|---|---|
| 1 | 2 (halts, 1 row fetched) | 200 | broken |
| 2 | 200 | 100 | 100% |
| 5 | 50 | 40 | 25% |
| 25 | 9 | 8 | 12% |

The cost is negligible at the default `--limit 25` and pathological below about
5. This is a real but bounded efficiency defect; the `--limit 1` halt is the part
that loses data.

### 4. What WO-2026-08-27-001 already fixed

Duplicate rows no longer reach `serial` output: `buildSerialEntries` dedupes
within a batch on `eventTime + identity` (`tools/telemetry:1892-1897`). So the
boundary row is fetched twice but emitted once. **This WO is about the fetch, not
the output** — the wasted query and the `--limit 1` halt.

`watch` uses the same paging and has no equivalent emission cap, so it pays the
same query amplification.

## Scope

1. Advance `pageEnd` so the boundary row is not re-fetched — for example by
   querying `eventTime BETWEEN :start AND :end` with an exclusive upper bound
   derived from the oldest row, or by keeping the inclusive bound and skipping
   the known boundary row when counting a page as full. Either is acceptable;
   the requirement is that each page yields up to `limit` *new* rows and that
   `--limit 1` makes progress.
2. Keep `visitedPageEnds` as a safety net against any future non-advancing case.
   It should stop firing in normal operation, not be deleted.
3. Preserve every truncation semantic established by WO-2026-08-27-001. That
   work order's matrix is the regression bar, not a suggestion — see Required
   Tests.
4. If `--limit 1` can now distinguish a complete single-row window from a
   truncated one, remove the conservative false positive and update the
   `docs/API.md` note (`docs/API.md:627`) that documents it. If ambiguity
   remains, leave both the behavior and the note as they are and say so.

## Acceptance Criteria

- `serial --limit 1` over a multi-row window fetches the whole window rather
  than halting after one row, confirmed by a query trace against a real CLI run.
- Query count for a window of N rows is `ceil(N / limit)` (± 1), confirmed by
  trace at `--limit` 2, 5 and 25 — no longer `N / (limit - 1)`.
- No row is fetched twice in a single `fetchWatchTimeline` call.
- **No regression to WO-2026-08-27-001's truncation matrix**, specifically:
  exact-limit complete windows at 2/3/5/25/100 report `truncated: false` with
  exactly N unique rows emitted; 26 and 200 at `--limit 25` report `truncated:
  true` with 25 emitted; `--limit 3000` over 2500 reports truncated with 2000
  emitted and over a complete 2000 reports complete; all three `--grep`
  no-match recovery windows report complete; `serial --limit 1 --grep <no-match>`
  over a multi-row window still reports truncated (or reports complete *only* if
  scope item 4 establishes the window was genuinely fully read).
- `watch` and `serial --follow` continue to emit each row exactly once, with the
  cursor advancing normally.
- `docs/API.md` and `docs/tools.md` accurate for whatever behavior results.

## Required Tests

Add to `tools/telemetry.test.js`, exercising real code paths with mocked
`awsJson`/`fetch`:

1. `--limit 1` over a multi-row Dynamo window fetches every row (fails today).
2. Query-count assertions at `--limit` 2, 5 and 25 over a known window size —
   assert on the number of mocked `awsJson` calls. These fail today.
3. No row appears twice across the pages of one `fetchWatchTimeline` call.
4. The full WO-2026-08-27-001 truncation matrix as listed in Acceptance Criteria,
   as explicit regression tests.
5. A `--follow` sequence asserting each row is emitted once and the cursor
   advances.

Fixture rules, unchanged from WO-2026-08-27-001 and non-negotiable — both were
violated during its investigation and produced false results: timestamps must be
**fixed** (never `Date.now()`-derived) and **distinct per device** (the Dynamo key
is `(deviceId, eventTime)`), and the mocked `awsJson` must return
`LastEvaluatedKey` while rows remain.
