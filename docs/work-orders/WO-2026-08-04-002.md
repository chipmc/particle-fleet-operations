# WO-2026-08-04-002: Follow-ups to `telemetry serial --start` (WO-2026-08-04-001)

## Context

WO-2026-08-04-001 added `--start`/reused `--until` on `telemetry serial`
(merged in PR #12). Investigation below re-checked the three gaps the draft
named, against current `main` (`eb581f2`).

## Investigation Findings (2026-08-04)

Investigated directly by reading source (`tools/telemetry`,
`tools/event-presentation.js`, `docs/API.md`, `scripts/package.json`) and
independently corroborated by `codex exec`. Both converged on the same
conclusions, which correct or narrow all three items in the original draft:

1. **Gap 1 (help text) is already fixed for `serial`, but not for
   `timeline`.** PR #12 already updated both `serial` help surfaces on
   `main`: the top-level usage summary (`tools/telemetry:139`) and the
   `serial`-specific help block (`:299`, `:312`), plus the shared global
   Options list (`:164`). There is nothing left to do for `serial`'s help
   text. What's actually still missing is `timeline`'s help — its
   top-level usage line (`:136`) and its command-specific Options list
   (`:263-266`) show only `--since`/`--hours`, with no mention of `--start`.
   This isn't a new gap; it's just gap 1 as originally scoped (serial) being
   moot, folded into gap 2's `timeline` work instead.

2. **`timeline --start` is silently accepted and silently ignored today —
   a real, if minor, pre-existing bug.** `--start`/`--until` parsing in
   `parseOptions` is global, not gated per subcommand (`tools/telemetry:384,
   386, 388`), so `timeline <device> --start <ISO>` parses without error.
   But `timeline`'s dispatch (`:93-99`) goes straight to `fetchTimeline()`
   with no validation step, and `fetchTimeline()` only ever sends `hours`+
   `limit` to the API (`:743-750`) — it never reads `options.startIso` or
   `options.until` in HTTP mode. (The local DynamoDB fallback path,
   `queryTimelineFromDynamo`, does read `options.start`/`options.end` —
   different property names than what `parseOptions` actually sets
   (`startIso`/`until`), so that fallback path doesn't pick them up either,
   confirmed by both investigations independently.) Net effect: today,
   `--start` on `timeline` does nothing, with no error to tell you so. This
   WO fixes that as a side effect of adding real `--start` support.

3. **Shared-helper question: partial reuse, not wholesale.** `serial` and
   `timeline` fetch fundamentally differently — `serial` walks backward
   through multiple paginated API calls via `fetchWatchTimeline()`
   (`:1792, 1939`) to accumulate enough raw (all-plane) events to reach
   `options.limit` *SERIAL-only* rows after client-side filtering.
   `timeline` is a single bounded fetch that already maps directly onto the
   API's own `start`/`end`/`limit` contract — it doesn't filter by kind, so
   it has no reason to page. Reusing `serial`'s `createSerialState()` /
   `fetchWatchTimeline()` for `timeline` would drag in cursor tracking,
   dedup, follow-mode, and backward pagination that `timeline` doesn't
   need, and (per finding 4 below) risks touching code `watch` also
   depends on. **Recommendation (both investigations agree): extract three
   small, pure, shared helpers** — (a) `--start`/`--since` mutual-exclusion
   validation, (b) resolving `{start, end}` from `startIso`/`sinceMs`/
   `until`/(`timeline`'s `hours` default), and (c) formatting the
   truncation-warning message — and keep the actual fetch/orchestration
   code separate per command. Do not route `timeline` through
   `createWatchState()`/`fetchWatchTimeline()`.

4. **`watch` is not fully independent today — a pre-existing PR #12 side
   effect, not something this WO introduces.** `watch` and `serial` share
   `createWatchState()` (`watch` calls it directly at `:1884`; `serial`
   calls it via `createSerialState()` at `:1785`). PR #12 added an
   `options.startIso` branch inside `createWatchState()` itself (`:1922`),
   which means `telemetry watch <device> --start <ISO>` **already** works
   today to shift `watch`'s initial cursor — undocumented, untested, and
   not something either WO asked for. It's also inconsistent: `watch`'s
   `includeInitialTimeline` flag is still keyed only on `sinceMs > 0`
   (`:1931`), not `startIso`, so the initial window's events would likely
   be marked seen but never actually displayed — a latent, currently-unused
   half-broken path. This WO does not need to fix it: as long as the new
   `timeline` work uses the recommended separate shared-helper design
   (finding 3) instead of touching `createWatchState()` /
   `fetchWatchTimeline()` / `fetchTimelinePage()`, `watch` is unaffected
   either way.

   **Decision (Chip, 2026-08-04): add the guard.** Rationale: the problem
   isn't that `watch --start` works, it's that it half-works — an
   undocumented, untested flag that silently swallows the initial window
   is a footgun for whoever finds it next, and this WO is already
   establishing a fail-loud pattern (mutual-exclusion errors, truncation
   warnings). Leaving `watch` as the one place that quietly does
   something-but-not-quite-right undercuts that consistency for a trivial
   fix cost. `watch --start <ISO>` must now error with a clear message
   (e.g. "`--start` is not supported for `watch`; use `--since`.").
   Implement this as a check at `watch`'s dispatch (`tools/telemetry:102-
   108`, before/inside `startWatch`), not inside `createWatchState()` —
   keeps the Protected Areas below intact.

5. **`docs/API.md` doesn't contain a literal false claim that `plane` is a
   query parameter** — the Query Parameters list for the endpoint
   (`docs/API.md:46-50`) only lists `hours`, `start`, `end`, `limit`;
   `plane` only appears under Response Fields (`:96`) as returned data.
   The correction needed is an **added clarification**, not a fix to wrong
   text: a note that the endpoint returns events across all planes in the
   window, and that `tools/telemetry serial`'s plane filtering happens
   client-side (`tools/event-presentation.js:15`, `:90`;
   `tools/telemetry:1803`), not via any server-side filter.
   Separately: the existing "From CLI Timeline Tool" section
   (`docs/API.md:577-596`) is **not** about `tools/telemetry` at all — it
   documents a different, legacy `npm run timeline` script
   (`scripts/package.json:10`). There is no existing section documenting
   `tools/telemetry`'s actual flags. This WO should add a new section for
   that, rather than trying to extend the stale migration-notes one (which
   is out of scope to fix/remove here).

## Scope Change

Given the above, this WO's Fix section becomes:

1. Add `--start <ISO8601>` and `--until` support to `timeline`, matching
   `serial`'s validation and truncation-warning behavior, via three shared
   pure helpers (mutual-exclusion check, window resolution, warning
   formatting) — not by routing `timeline` through `serial`'s
   paginated/cursor-based fetch path. Update `timeline`'s two help
   surfaces (`tools/telemetry:136`, `:263-266`) accordingly. No further
   change needed for `serial`'s help text — already correct on `main`.
2. Do not touch `createWatchState()`, `fetchWatchTimeline()`, or
   `fetchTimelinePage()`. Add an explicit guard at `watch`'s dispatch so
   `watch --start <ISO>` errors with a clear message instead of silently
   half-working (see decision in finding 4 above).
3. Add a clarifying note to `docs/API.md` (near `:96` and/or the Query
   Parameters list) that plane filtering is client-side, not a query
   param — this is new clarifying text, not a factual correction of
   existing wording. Add a new section documenting `tools/telemetry`'s
   actual `--start`/`--until`/`--since` flags on `serial` and `timeline`
   (the existing CLI section at `:577` is about an unrelated legacy tool
   and is out of scope to modify).

## Acceptance Criteria

- `telemetry timeline <name-or-device-id> --start <ISO8601> [--until
  <ISO8601>]` returns events within `[start, until-or-now]`, sent via the
  API's `start`/`end` params (or the DynamoDB fallback's equivalent),
  fixing the current silent no-op.
- `timeline --since` + `--start` together errors, matching `serial`'s
  existing mutual-exclusion behavior.
- Truncation warning appears on `timeline` when returned events reach
  `--limit`.
- `timeline --help` and top-level `--help` document `--start`/`--until`
  for `timeline`.
- `watch` behavior is unchanged for existing flags (no edits to
  `createWatchState`/`fetchWatchTimeline`/`fetchTimelinePage`);
  `watch --start <ISO>` now errors with a clear message instead of
  silently half-working.
- `docs/API.md` gains an explicit client-side-filtering clarification and
  a new section documenting `tools/telemetry`'s real `--start`/`--until`
  flags; the unrelated legacy-CLI migration note is left alone.

## Required Tests

- `timeline --start` (no `--until`) returns the correct window, defaulting
  end to now.
- `timeline --start` + `--until` returns only rows within `[start, until]`.
- `timeline --start` + `--since` together errors.
- Truncation warning appears on `timeline` when the row cap is hit; absent
  when it isn't.
- Existing `timeline --since`/`--hours` regression tests still pass
  unchanged.
- `watch --start <ISO>` errors with a clear message.
- Existing `watch` behavior (no `--start`) is unaffected (regression
  check).

## Permitted Files

- `tools/telemetry` — new shared helpers (validation, window resolution,
  truncation-warning formatting), `timeline` dispatch/fetch wiring,
  `timeline`'s two help-text surfaces, and the `watch --start` rejection
  guard at `watch`'s dispatch block.

## Protected Areas

  `tools/telemetry` — no changes (this is what keeps `watch` unaffected).
- `tools/event-presentation.js` — no changes; classification logic is

- `docs/API.md`'s existing "From CLI Timeline Tool" migration-notes
  section (`:577-596`) — leave as-is; it documents a different, legacy
  tool and correcting it is out of scope here.
- `serial`'s help text (already correct on `main`) — no changes needed.
